# 16. 호스트 방화벽 정책은 비공개 저장소를 정본으로 두고, 병합하면 적용하며, 정기 비교로 드리프트를 보고한다

호스트 방화벽(iptables·firewalld·UFW)은 프로비저닝(`security` 롤)과 손 작업이 섞여 쌓였다. 어떤 서버가 어떤 서버에 무엇으로 통신할 수 있는지 한곳에서 볼 수 없고, 변경의 승인·검토 이력과 정기 검토 증적이 없으며, 손으로 바꾼 규칙(드리프트)을 알아낼 방법이 없다. 이 저장소는 공개라서 서버 목록·주소·포트·규칙을 둘 수 없다. 그래서 **정책(원하는 상태)의 정본을 별도 비공개 저장소(`firewall-policy`)에 둔다**. 추적은 이 저장소의 스펙 이슈 #589와 그 티켓에서 하고, 형식의 정본은 비공개 저장소의 `docs/FORMAT.md`다.

1. **정본은 비공개 저장소다.** 이 저장소에는 서버 목록·주소·규칙을 두지 않는다. 비공개 저장소는 사내 Forgejo에 있고 접속 자격은 OpenBao `secrets/`에만 둔다.
2. **GitOps 흐름.** PR(문법·의미 검증, 서버에 접속하지 않는 렌더링 diff, 필수 리뷰) → 병합 → Forgejo 웹훅(서명 검증) → Semaphore 적용 템플릿. 별도의 주기 템플릿이 실제 상태를 수집해 정책과 비교하고 이메일·알람으로 보고한다.
3. **정책은 IP 기반 한 줄 규칙과 별칭이다.** 규칙은 받는 호스트별 파일에 두고, 규칙 안에는 호스트 이름과 인벤토리 그룹을 쓰지 않는다. IP가 진실이고 별칭은 라벨이다. 그래서 정책의 의미는 인벤토리 변경만으로 바뀌지 않고 반드시 PR 승인을 거친다. 규칙마다 목적·담당을 적고 선택으로 티켓·만료일(`until`, 지나면 검증 실패)·재검토 기한(`review`, 지나면 보고)을 둔다.
4. **관리 범위와 단계.** 호스트 방화벽 전체가 아니라 전용 체인·영역만 관리하고 기존 규칙은 건드리지 않는다. 호스트마다 `observe`(비교만, 기본)와 `enforce`(적용)를 두고 보고만 → 카나리 → 전체 순서로 넓힌다. 컨테이너 엔진이 만드는 방화벽 체인은 바꾸지 않고 게시 포트를 보고만 한다.
5. **자기 차단 방지.** 예약 별칭 `always_allow`(실행 서버·사무실)는 호스트 파일이 있는 모든 호스트의 관리 포트에 항상 허용되고 정책으로 지울 수 없다. 적용은 런타임 반영 → 자동 되돌림 타이머 → 접속 확인 → 영구 저장 순서이고, 카나리부터 단계적으로 넓히며 첫 실패에서 멈춘다. 병합된 커밋만 적용한다. 정책 저장소·실행 서버 자체와 방화벽 관리 제외 호스트는 적용 대상이 아니다.
6. **드리프트는 정책 모델과 관측 모델의 비교용 정규형을 비교한다.** 두 모델은 주소(CIDR) 기반의 같은 모양이고, 같은 받는 호스트·프로토콜·포트의 출발지는 합쳐 비교한다. 정책에만 있으면 "누락", 관측에만 있으면 "초과"다. 컨테이너 게시 포트는 비교하지 않고 따로 보고한다. 알람은 직전 실행과 달라졌을 때만 보낸다.
7. **도구.** Terraform/OpenTofu는 쓰지 않는다. Ansible(Semaphore 실행)과 생성 스크립트를 쓴다. iptables·nftables 렌더러는 Aerleon을 후보로 시험해 채택을 결정하고, firewalld·UFW 렌더러는 직접 만든다.
8. **이 저장소와의 경계.** 정책을 적용하기 전까지 `security` 롤의 방화벽 태스크는 그대로 동작한다. 호스트를 `enforce`로 넘길 때 그 호스트를 `security` 롤의 방화벽 관할에서 빼고 기록한다(카나리 적용 티켓에서 정한다).

## Considered Options

- **Terraform/OpenTofu**: 호스트 iptables를 다룰 쓸 만한 provider가 없다(유일한 provider는 호스트마다 API 서비스를 띄운다). Semaphore의 state backend는 유료 기능이고, 객체 저장소의 조건부 쓰기 지원(state 잠금)이 확인되지 않았다.
- **`security` 롤 확장**: 이 저장소가 공개라 서버 정보를 둘 수 없고, 방화벽 변경 승인 이력이 다른 코드 변경과 섞인다.
- **호스트 이름·그룹 기반 정책**: 인벤토리 변경만으로 허용 범위가 바뀌고, 방화벽이 실제로 보는 주소(예: 사무실에서 오는 SNAT된 주소)와 어긋난다.
- **Ansible 체크 모드로 드리프트 판정**: Raw Provisioning Path 호스트(ADR-0005)에서는 체크 모드를 쓸 수 없다. 수집한 상태를 비교하면 모든 호스트를 같은 방식으로 본다.
- **관측 없이 정책부터 적용**: 첫 정책이 현실과 다르면 운영 중인 통신을 끊는다. 관측에서 첫 정책 초안을 만들어 드리프트 0으로 시작한다.
- **표준 형식 하나를 그대로 채택**(IETF ACL 모델, OpenConfig ACL, Kubernetes NetworkPolicy): 호스트 방화벽 렌더링에 바로 맞는 표준이 없어 개념(규칙 단위, 이름 붙인 주소 집합, 포트 범위, 허용 목록)만 빌렸다.

## Consequences

- 병합이 곧 운영 변경이다. `main` 보호와 병합 리뷰 필수, 웹훅 서명과 시크릿 관리가 전제 조건이고 티켓에 포함돼 있다.
- 정책의 의미가 IP에 묶인다. 서버의 주소가 바뀌면 별칭을 PR로 고쳐야 하고, 검증기가 별칭의 주소를 인벤토리 주소와 대조해 경고한다.
- 정책 파일이 없는 호스트는 `observe`로만 쓸 수 있다.
- 컨테이너 엔진이 게시한 포트는 정책으로 통제하지 못하고 보고만 한다. 이 범위에서는 컨테이너 엔진의 방화벽 체인을 바꾸지 않는다(`security` 롤에 있는 컨테이너 엔진 체인 관리기와의 관계는 `enforce` 호스트의 관리 경계를 정할 때 함께 정한다).
- 수집은 Host Audit의 읽기 전용 정의를 따르므로 ADR-0009의 원칙은 그대로다. 적용기만 호스트 상태를 바꾸고 `enforce` 호스트에 한정된다.
- OS 계열별 렌더러가 가장 큰 작업이다. 첫 대상 계열과 카나리 호스트는 사람이 정한다(#608).
- Semaphore가 커밋 해시를 직접 체크아웃하는지는 확인하지 못했다. 적용 직전에 `main`의 HEAD가 웹훅이 알려 준 커밋과 같은지 비교하는 방법으로 대신한다.
- 방화벽 드리프트는 Configuration Drift(Git이 선언한 호스트 상태와의 차이)와 다른 개념이다(`CONTEXT.md`의 Firewall Drift).
