# 18. 플레이북을 기능별 저장소로 나누고, 취약점 점검(`vulnerability`)부터 옮긴다

이 저장소는 프로비저닝, 에이전트, 백업, 관측 설정, 감사를 한곳에 두고 있다. 기능마다 테스트·릴리스·접근 주체가 다른데 한 저장소가 모두 묶고 있어, 한 기능을 바꿔도 전체 검증을 돌려야 한다. 그래서 **세부 플레이북을 기능별 공개 저장소로 하나씩 나눈다**. 첫 대상은 Host Audit의 취약점 점검(KISA·패키지·스위치, 조치 가이드, 직전 정기 보고서 대비 비교와 악화 알림)이며 새 저장소는 `ppzxc/vulnerability`다. 추적은 그 저장소의 스펙 #1과 티켓 #2~#13이다. 진행 현황과 체크리스트의 정본은 `README.md` 5절이다.

1. **양식.** 새 저장소는 `ansible-creator init playbook` 양식과 인접 컬렉션 `ppzxc.<이름>`을 쓴다. 판정 로직은 컬렉션 `module_utils`의 순수 Python으로 두고, filter와 module은 얇은 어댑터다.
2. **로컬 우선.** 설정이 없으면 로컬 설정과 로컬 저장으로 동작한다. 설정 블록이 있을 때만 OpenBao, S3(RustFS), 메일, webhook을 쓴다. 인증 값은 환경 변수로만 받는다.
3. **테스트 먼저.** 기능을 옮기기 전에 이 저장소의 테스트를 옮기고(red) golden으로 특성화한 뒤 코드를 옮긴다(green). fixture는 가명만 쓴다. 테스트 경계는 순수 판정 엔진과 molecule 실제 playbook E2E 두 개다.
4. **이전 중 동결.** 옮기는 기능은 새 저장소의 첫 커밋부터 이 저장소에서 변경을 멈춘다. 동작은 그대로 둔다.
5. **병행·대조 후 삭제.** Semaphore에 새 템플릿을 만들어 같은 날 병행 실행하고 결과를 대조한다. 통과한 뒤에만 이 저장소에서 지운다. 기존 증적과 Baseline은 변환하지 않는다.
6. **공통 기반은 두 번째 저장소에서 추출한다.** 처음에는 필요한 부분을 복사한다. 두 번째 저장소(`configuration-backup`)를 나눌 때 `ppzxc.infra_common`으로 추출한다.
7. **공개 저장소 규칙.** 새 저장소에도 IP·호스트·주소·점검 결과 같은 인프라 상세를 넣지 않는다.

## Considered Options

- **모노레포 유지**: 기능별 검증·릴리스 분리가 안 된다.
- **한 번에 전부 분리**: 병행 대조 없이 운영 점검이 끊길 위험이 크다. 기능 하나씩 옮기며 방법을 다듬는다.
- **공통 기반을 먼저 추출**: 쓰는 곳이 하나뿐일 때 추상화하면 잘못 자른다. 두 번째 저장소에서 실제 중복을 보고 추출한다.

## Consequences

- ADR-0009(Host Audit)의 취약점 점검 부분은 대조 통과 뒤 새 저장소가 이어받는다. 이 저장소의 `docs/host_audit*.md`와 `cisco_backup`의 audit 경로는 그때 정리한다.
- 남는 Host Audit(Asset Inventory, Log Review 서명 등)과 나머지 플레이북은 README 5.3의 순서로 차례로 나눈다.
- 이 저장소의 3-Way Spec 검증과 테스트는 이전된 기능만큼 줄어든다.
