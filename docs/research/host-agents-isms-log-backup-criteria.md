## 적용 범위: ISMS와 ISMS-P

안내서 p.2~3: 인증기준은 3개 영역, 101개 항목입니다. **ISMS는 "1. 관리체계 수립 및 운영"(16개)과 "2. 보호대책 요구사항"(64개), 합계 80개 기준을 적용받습니다.** "3. 개인정보 처리 단계별 요구사항"(21개)은 ISMS-P에만 적용됩니다.

이 문서가 다루는 2.9.x, 2.10.x, 2.11.x, 2.12.x는 모두 **영역 2**에 속하므로 **ISMS에도 그대로 적용됩니다.** 다만 영역 2 항목 안에도 "개인정보처리시스템"에 한정한 확인사항이 섞여 있습니다(예: 2.9.4의 세 번째 확인사항). 이 항목들의 근거는 「개인정보의 안전성 확보조치 기준」(개인정보보호위원회 고시)입니다. 이 고시는 인증 여부와 관계없이 모든 개인정보처리자에게 적용되는 **법적 의무**입니다. 따라서 ISMS 심사 범위의 서버가 개인정보처리시스템이면 ISMS 심사에서도 이 부분을 점검한다고 봐야 합니다. "ISMS라서 개인정보 접속기록은 안 본다"고 가정하면 안 됩니다.

> 고시 원문(제8조 접속기록의 보관 및 점검, 제11조 재해·재난 대비 안전조치)은 이번에 law.go.kr에서 받지 못했습니다. 아래 수치는 **안내서에 인용된 형태 그대로** 옮긴 것이고, 조문 원문은 따로 확인하지 않았습니다.

## 핵심 답변

1. **일반 시스템·보안 로그의 보존기간은 ISMS 기준에 숫자가 없습니다.** 2.9.4는 로그유형, 보존기간, 보존방법을 **조직이 정하라**고 요구합니다(기준 명시). 심사원은 "내부 기준에 기간을 정했는가, 실제로 그 기간만큼 남아 있는가"를 봅니다(결함사례 2, 5).
2. **보존기간 숫자(1년/2년)와 점검 주기(월 1회)는 개인정보처리시스템 접속기록에만 있습니다.** 근거는 안전성 확보조치 기준 제8조입니다.
3. **무결성**: 로그는 위·변조, 도난, 분실되지 않게 보관하고 접근권한을 최소화해야 합니다(기준 명시). 방법은 "별도 저장장치로 백업하고 접근권한을 최소화"하는 것입니다(해설). WORM 매체나 MAC/전자서명 값을 따로 보관하는 방식은 **개인정보 접속기록의 예시**로만 나옵니다.
4. **백업**: 대상, 주기, 방법, 보관장소, 보관기간, 소산 절차를 수립하고 이행해야 합니다. **정기 복구 테스트**와 **중요정보 백업매체의 물리적 분리 소산**도 요구됩니다(기준 명시). 주기와 테스트 빈도는 숫자가 없어 내부 기준으로 정합니다.
5. **시간 동기화**(2.9.6): 표준시각 동기화와 그 **주기적 점검**이 요구됩니다(기준 명시).

## 항목별 상세

### 2.9.4 로그 및 접속기록 관리 (p.140~142)

| 내용 | 태그 |
|---|---|
| 서버, 응용프로그램, 보안시스템, 네트워크시스템의 사용자 접속기록, 시스템로그, 권한부여 내역 등에 대해 로그유형, 보존기간, 보존방법을 정하고 위·변조, 도난, 분실되지 않게 보존·관리 | 기준 명시 |
| 로그관리 절차를 수립하고 필요한 로그를 생성·보관 | 기준 명시 (확인사항 1) |
| 로그를 안전하게 보관하고 로그 접근권한을 최소화 | 기준 명시 (확인사항 2) |
| 개인정보처리시스템 접속기록은 법적 필수 항목을 모두 포함해 일정기간 보관 | 기준 명시 (확인사항 3, 개인정보처리시스템 한정) |
| 주요 로그유형 예시: 시스템 이벤트 로그(시작, 종료, 상태, 에러), 네트워크 이벤트 로그(IP 할당, 트래픽), 보안시스템 로그(관리자 접속, 룰셋 변경), **보안관련 감사 로그(사용자 접속기록, 인증 성공/실패, 파일 접근, 계정·권한 등록·변경·삭제)**, 개인정보처리시스템 접속기록 | 해설·예시 |
| 시스템·장비별로 로그 형태, 보존기간, 보존(백업) 방법을 정의 | 해설 |
| "로그기록은 스토리지 등 **별도 저장장치를 사용하여 백업**하고 접근권한 부여는 최소화하여 비인가자에 의한 위·변조 및 삭제 등이 발생하지 않도록" | 해설 |
| 개인정보 접속기록 필수 항목: 식별자(계정), 접속일시(연월일 시분초), 접속지 정보(IP), 처리한 정보주체 정보, 수행업무(조회, 변경, 입력, 삭제, 출력, 다운로드) | 해설 (고시 제8조 인용) |
| 개인정보 접속기록 보존: 정보주체 5만 명 이상, 고유식별정보·민감정보 처리, 또는 기간통신사업자이면 **최소 2년**, 그 밖에는 **최소 1년** | 해설 (고시 제8조 인용, 개인정보 한정) |
| 안전한 보관 예시: 별도 보조저장매체, 저장장치, **오브젝트 스토리지**에 상시 백업. WORM 등 덮어쓰기 방지 매체 사용. 수정 가능한 매체면 MAC값이나 전자서명값을 **별도 장비**에 보관 | 해설·예시 (개인정보 접속기록 맥락) |
| 증거자료 예시: 로그관리 절차, 로그기록 내역, **로그 저장장치 접근통제 내역**, 개인정보 접속기록 내역 | 해설 |

결함사례 중 Linux 서버와 직접 관련된 것:

- 사례 1: 로그 기록 대상, 방법, 보존기간, 검토 주기, 담당자에 대한 세부 기준이 없음
- 사례 2: 중요 로그의 최대 크기를 충분히 설정하지 않아 **내부 기준 기간만큼 보관되지 않음**. 로컬 journald와 logrotate 용량 설정도 여기에 해당합니다.
- 사례 3: "**중요 Linux/UNIX 계열 서버에 대한 로그 기록을 별도로 백업하거나 적절히 보호하지 않아 사용자의 명령 실행 기록 및 접속 이력 등을 임의로 삭제할 수 있는 경우**"
- 사례 5: 로그 서버 용량이 부족해 접속기록이 2개월치만 남음

### 2.9.5 로그 및 접속기록 점검 (p.143~144)

| 내용 | 태그 |
|---|---|
| 오류, 오·남용(비인가접속, 과다조회), 부정행위 등 이상징후를 인지할 수 있게 로그 검토 주기, 대상, 방법을 포함한 검토·모니터링 절차를 수립·이행 | 기준 명시 |
| 검토·모니터링 결과를 책임자에게 보고하고, 이상징후가 있으면 절차에 따라 대응 | 기준 명시 |
| 개인정보처리시스템 접속기록은 법령 주기(**월 1회 이상**)로 점검 | 기준 명시 + 해설 (개인정보 한정) |
| 절차에 담을 요소: 검토 주기, 대상, 기준·방법, 담당자·책임자, 이상징후 대응절차 | 해설 |
| 증거자료 예시: 로그 검토·모니터링 절차, **검토 결과(검토 내역, 보고서)**, 이상징후 대응 증거 | 해설 |
| 결함사례 1: 휴일 새벽 접속, 우회경로 접속 같은 이상접속에 대한 **모니터링 및 경고·알림 정책**이 없음 | 해설 |
| 결함사례 2: 기준은 있는데 실제 검토 내역이 없음 | 해설 |

일반 서버 로그의 검토 주기는 숫자가 없습니다. 내부 기준으로 정하고, 그 주기대로 검토했다는 기록을 남겨야 합니다.

### 2.9.3 백업 및 복구관리 (p.138~139)

| 내용 | 태그 |
|---|---|
| 가용성과 데이터 무결성을 위해 백업 대상, 주기, 방법, 보관장소, 보관기간, 소산 등 절차를 수립·이행하고 사고 시 적시에 복구 | 기준 명시 |
| 백업 대상, 주기, 방법, 절차를 포함한 백업·복구절차를 수립·이행 | 기준 명시 (확인사항 1) |
| 완전성, 정확성, 복구절차 적절성을 확인하기 위한 **정기 복구 테스트** | 기준 명시 (확인사항 2) |
| 중요정보 백업매체를 재해·재난에 대비해 **물리적으로 떨어진 장소에 소산** | 기준 명시 (확인사항 3) |
| 절차 요소: 백업대상 선정기준, 백업 담당자·책임자, 대상별 주기와 보존기한, 방법(백업시스템, 수동), 매체 관리(라벨링, 보관장소, 접근통제), 복구 절차, **백업관리대장** | 해설 |
| 주요 백업 대상 예시: 중요정보(개인정보, 기밀), 중요 DB, **각종 로그(감사로그, 이벤트 로그, 보안시스템 이벤트 로그)**, **환경설정 파일** | 해설·예시 |
| 복구테스트: 계획(주기, 시점, 담당자, 방법), 시나리오, 실시와 결과 보고, 문제점이 나오면 개선계획 수립·이행 | 해설 |
| 소산: 운영 시스템과 백업시스템이 있는 곳에서 물리적으로 떨어진 곳에 보관, 관리대장으로 이력(일자, 매체, 내용) 관리, 주기 점검, 소산장소 보안(내화, 접근통제) | 해설 |
| 증거자료 예시: **백업 및 복구 절차**, **복구테스트 결과**, **소산백업 현황** | 해설 |
| 결함사례 2: 법적 요구로 장기(6개월, 3년, 5년 등) 보관이 필요한 대상이 정책대로 보관되지 않음 | 해설. 이 숫자들은 다른 법령에서 온 것으로 보이며 ISMS 자체 수치가 아닙니다. 근거 법령은 확인하지 않았습니다. |
| 결함사례 3: 내부 지침상 별도 백업 대상인 보안시스템 정책·로그를 백업하지 않음 | 해설 |
| 결함사례 4: 지침에는 주기 복구 테스트가 있는데 **장기간 실시하지 않음** | 해설 |

백업 주기, 보관기간, 복구 테스트 빈도는 숫자가 없습니다. 심사의 초점은 "정한 대로 했는가"입니다(결함사례 4).

### 2.9.6 시간 동기화 (p.145)

| 내용 | 태그 |
|---|---|
| 로그 정확성을 위해 정보시스템 시각을 표준시각에 동기화 | 기준 명시 |
| 동기화가 정상인지 **주기적으로 점검**. 오류, OS 재설치나 설정 변경으로 적용이 빠졌는지 확인 | 기준 명시 + 해설 |
| 증거자료 예시: 시간 동기화 설정, 주요 시스템 동기화 증거 | 해설 |
| 결함사례 2: 내부 NTP로 설정했는데 일부 시스템이 동기화되지 않고 원인 분석도 없음 | 해설 |

### 관련 항목

- **2.10.1 보안시스템 운영 (p.148~150)**: 보안시스템 이벤트 모니터링 절차, 주기적인 보안시스템 접속로그 분석, 정책 신청·승인·적용 기록 보존(책임추적성). 서버 보안시스템 예시로 시스템 접근제어와 SecureOS가, 기타 예시로 SIEM이 나옵니다. (기준 명시 + 해설)
- **2.11.3 이상행위 분석 및 모니터링 (p.175~176)**: 주요 정보시스템, 네트워크, 보안시스템의 이벤트 로그를 **수집하여 분석·모니터링**하고, 이상행위 판단 기준과 임계치를 정의해 후속 조치를 합니다(기준 명시). 수집 대상과 범위, 방법, 담당자, 보고 체계, 대응 절차를 갖춘 "수집·분석 체계"를 요구하고, 규모가 크면 24시간 실시간 모니터링을 고려하라고 합니다(해설). 중앙 로그 수집(otelcol에서 OpenObserve로)이 직접 대응하는 항목입니다.
- **2.11.4 사고 대응 훈련 및 개선 (p.177)**: 모의훈련 **연 1회 이상**. 로그·백업 항목과 달리 기준에 숫자가 **명시된** 예입니다.
- **2.12.1 재해·재난 대비 안전조치 (p.181~183)**: 핵심 시스템별 **RTO와 RPO 정의**(기준 명시). 결함사례 5는 "복구 목표시점과 백업정책(대상, 주기)이 연계되지 않은 경우"입니다. 백업 주기는 RPO에서 도출해야 합니다.
- **2.12.2 재해 복구 시험 및 개선 (p.184~185)**: 재해 복구 시험계획(일정, 참여인원, 범위, 방법, 시나리오)을 세우고 정기적으로 시험합니다. 증거는 시험 계획서와 결과서입니다. 주기 숫자는 없습니다.

## 이 저장소 현황과 대조 (map #8 후속 티켓 입력용 관찰, 결정 아님)

1. **소산 (2.9.3 확인사항 3)**: map에 따르면 RustFS는 OpenObserve와 같은 서버에서 동작합니다. 그 서버가 대상 호스트와 **같은 장소(IDC, 랙)** 에 있으면 RustFS 백업만으로는 "물리적으로 떨어진 장소 소산"을 충족하지 못합니다. 중요정보를 담은 백업이면 원격지 복제(버킷 복제, 2차 repository) 또는 소산 절차가 필요합니다. 백업 저장소 grilling 티켓에서 다룰 내용입니다.
2. **무결성 (2.9.4 확인사항 2)**: 로그를 호스트 밖의 OpenObserve로 보내고 그곳의 접근권한을 최소화하면 해설의 "별도 저장장치 백업 + 접근권한 최소화"에 직접 대응합니다. 결함사례 3(로컬에서 명령 기록 삭제 가능)을 막는 핵심 통제이기도 합니다. RustFS object lock(WORM)이나 해시 체인은 개인정보 접속기록의 **예시**일 뿐이며, 일반 로그에는 **권고** 수준입니다.
3. **`otel_system_logs` 차이** (`roles/monitoring/defaults/main.yml`):
   - 명령 실행 기록: `roles/security/templates/audit.rules.j2`에 `execve` 규칙(`-k exec_log`)이 이미 있고, `/var/log/audit/audit.log`도 수집 목록에 있습니다. 결함사례 3의 "명령 실행 기록"은 커버됩니다.
   - 접속 이력: `/var/log/secure`와 `/var/log/auth.log`는 텍스트 로그로 수집하지만, **`wtmp`, `btmp`, `lastlog`(바이너리)** 는 목록에 없습니다. filelog로는 읽을 수 없으므로 auditd와 secure/auth.log로 충분하다고 문서화하거나 별도 방법을 정해야 합니다.
   - **journald**: 목록에 journald 소스가 없습니다. rsyslog를 기본 설치하지 않는 배포판(예: 최소 설치 Debian 12 이상)에서는 `/var/log/syslog`와 `/var/log/auth.log`가 없을 수 있어 시스템, 인증 로그가 빠질 수 있습니다. OTEL 수집 표준 티켓에서 확인해야 합니다.
   - 로컬 보존: `roles/common`이 journald를 `SystemMaxUse=10G`, `MaxRetentionSec=3month`로 제한합니다. 로컬은 3개월, 장기 보존은 OpenObserve가 담당한다는 식으로 **보존 책임을 문서에 명시**해야 결함사례 2와 5에 대응할 수 있습니다.
4. **백업 대상 (2.9.3 예시)**: 해설 예시에 "환경설정 파일"과 "각종 로그"가 있습니다. restic 기본 include에 `/etc`를 넣을 근거가 됩니다. 로그를 OpenObserve로 보내는 것도 로그 백업으로 볼 수 있는지는 문서로 정해 두면 됩니다.
5. **시간 동기화 (2.9.6)**: `roles/common`이 chrony(CentOS 6은 ntp)를 설정하고 서비스를 기동합니다(`COMMON-008`, `COMMON-009`). 설정 증거는 있습니다. **주기적 점검** 증거는 없으므로, otelcol hostmetrics나 chrony 상태로 동기화 이상을 감시하면 점검 증거로 쓸 수 있습니다(권고).
6. **복구 테스트 (2.9.3, 2.12.2)**: map의 결정("restore는 runbook만")은 기준과 충돌하지 않습니다. 기준은 **정기 실시 + 결과 보고 + 개선**을 요구할 뿐 자동화를 요구하지 않습니다. runbook에는 주기(내부 기준으로 정함), 시나리오, 결과서 양식, 보고 대상을 담아야 합니다. 주기를 정한 뒤에는 결함사례 4 때문에 **실제로 그 주기대로 해야** 합니다.
7. **백업 결과 관측성**: restic 성공/실패 이력을 OpenObserve로 보내면 "백업관리대장, 백업 결과 이력" 증거로 쓸 수 있습니다(권고).
