# 백업 복원 시험과 서버 밖 사본 런북 (#374, Spec #364 / Ticket-7)

서버 손실에 대비해 (1) 백업 복호용 암호·시크릿 저장소 데이터·시크릿 파일을 운영자 로컬 암호 관리 도구(KeePassXC)에 두고, (2) 백업에서 실제로 복원되는지 시험하고, (3) 백업이 한 서버·한 볼륨에만 있는 위험과 서버 밖 복제 후보를 정리한다. 복제 구현은 이 문서의 범위 밖이다.

공개 저장소이므로 주소·포트·접근키·서버 이름과 볼륨 구성은 이 문서에 쓰지 않는다. 기록은 모두 비공개 경로(`~/.local/share/infra-automation/sec-364-apply/374/`)에 두고 이슈에는 통과 여부만 적는다.

## 1. 단일 서버·단일 볼륨 위험

호스트 백업은 호스트마다 전용 버킷을 가진 하나의 RustFS 저장소로 모인다([backup.md](../backup.md) §1). 그래서 저장소가 놓인 서버와 그 볼륨이 모든 호스트 백업의 단일 장애점이다.

| 위험 | 영향 | 현재 완화 | 남는 위험 |
|---|---|---|---|
| 저장소 서버 하드웨어 장애(컨트롤러, 전원, 메인보드) | 모든 호스트의 백업 조회·복원 불가 | 없음(서버 밖 사본 없음) | 복구 시간이 서버 수리·교체에 묶임 |
| 볼륨 손실(디스크 다중 장애, 파일시스템 손상) | 백업 데이터 영구 손실 | 하드웨어 RAID 1+0(디스크 1개 장애 허용). 쓰기 캐시는 백업 전원이 없어 꺼져 있음 | RAID는 삭제·손상·랜섬웨어를 막지 못함 |
| 호스트 침해 후 백업 삭제 | 해당 호스트 스냅샷 손실 | 호스트 키는 `locks/*` 외 삭제 불가([backup-host-key-scope.md](backup-host-key-scope.md)) | 같은 이름 덮어쓰기(변조)는 막지 못함. 월 1회 `check --read-data-subset`이 탐지 |
| 저장소 서버 침해 | 전 호스트 백업 삭제·변조 | 관리 접점 루프백 제한, SSH 출발지 제한([#364](https://github.com/ppzxc/infra-automation/issues/364)) | Object Lock 사용 불가(RustFS 제약). 서버 밖 사본이 없으면 복구 수단이 없음 |
| 복호 암호·시크릿 저장소 데이터 손실 | 백업이 남아 있어도 복호 불가 | 운영자 KeePassXC 보관(§2) | 보관 후 갱신 누락 |

서버 밖 사본이 없는 동안은 저장소 서버 손실이 곧 모든 호스트 백업의 손실이다. 이 위험은 복제를 구현하기 전까지 **수용 중인 위험**으로 남기고, 재검토일을 운영 기록에 둔다.

### 서버 밖 복제 후보 (결정 필요, 구현은 별도 이슈)

| 후보 | 방식 | 장점 | 단점·전제 |
|---|---|---|---|
| A. 저장소 측 S3→S3 복제 | 다른 서버의 RustFS 또는 S3 호환 저장소로 서버 측 복제 | 호스트 키·restic 변경 없음. [backup.md](../backup.md) §3이 이미 "전제조건"으로 적은 방식 | 대상 서버와 용량 필요. RustFS의 복제 기능 지원 여부 확인 필요 |
| B. 중앙 유지보수 러너의 `restic copy` | Repo Maintenance 실행 뒤 호스트별 저장소를 별도 저장소로 복사 | 복호 암호만 있으면 복원 가능. 저장소 종류를 가리지 않음 | 호스트별 암호 33개를 러너가 다뤄야 함. 실행 시간 증가 |
| C. 사내 NAS 정기 복사 | 중앙 러너에서 NAS로 rsync·rclone | 구성이 단순 | 같은 건물·망이라 사고 범위를 공유. NAS 인증 정보 관리 |
| D. 외부 오브젝트 스토리지 | B의 대상을 외부 서비스로 | 장소가 분리됨 | 비용, 반출 승인, 전송 시 암호화 확인 |
| E. 오프라인 매체 월 1회 | 가장 중요한 저장소만 외장 매체로 | 침해와 격리됨 | 수동 작업, 최신성 낮음 |

후보 결정은 용량(전체 저장소 크기), 보존 기간, 반출 가능 여부를 확인한 뒤 운영자가 한다. 복제본에도 같은 삭제 제한 원칙(쓰기 전용 키)이 필요하다.

## 2. 운영자 로컬 보관 (KeePassXC)

보관 대상과 위치:

| 대상 | 원천 | KeePassXC 위치 | 비고 |
|---|---|---|---|
| 호스트별 restic 복호 암호, 유지보수 키, 감사·수집 키 등 KV 시크릿 | OpenBao KV(`infra/prod/host`의 `secret`) | `Backup/OpenBao/infra/prod/host/secret/<경로>` | 항목마다 원본 JSON을 `bao_json`에 두고 키별 필드를 함께 둔다 |
| 시크릿 저장소 데이터 스냅샷 | 시크릿 저장소 서버 | `Backup/OpenBao/snapshots/<날짜>` | 문자열이 아니라 파일이므로 첨부로 둔다. 읽기 전용 AppRole로는 만들 수 없고 관리 권한이 필요하다 |
| 시크릿 파일(서비스 `.env`, 수동 실행 스크립트 등) | 두 핵심 서버 | `Backup/files/<서버>/<경로>` | 경로 후보는 [#375 소비자 목록](secret-file-permissions.md)과 비공개 노트에서 정한다. 파일 값은 첨부로만 둔다 |

규칙:

- 마스터 비밀번호는 운영자만 안다. 작업 중 파일로 건넨 경우 작업 직후 삭제한다.
- KeePassXC 데이터베이스는 항목 변경 전에 시각이 붙은 사본(0600)을 만들고, 롤백은 그 사본 복원이다. 항목 단위 되돌림은 KeePassXC 이력으로 한다.
- OpenBao에서 읽을 때는 읽기 전용 AppRole을 쓴다. 이 AppRole은 `list`와 `metadata`를 읽지 못하므로 경로를 직접 지정해 읽고, 버전은 읽기 응답의 `metadata.version`으로 비교한다.
- 비교는 `bao_json`의 해시나 키 집합으로 한다. 값은 화면·로그·이슈에 남기지 않는다.
- 갱신 누락을 막기 위해 호스트 추가·시크릿 변경 뒤 이 절의 갱신을 점검 목록에 넣는다(분기 복원 시험 때 같이 한다).

## 3. 복원 시험

[ADR-0006](../adr/0006-host-agents-otelcol-resticprofile.md) §2.11의 분기 절차를 실제로 한 번 수행하고 결과를 남긴다. 시험은 **임시 경로에만** 쓰고 운영 데이터를 덮어쓰지 않는다.

### 3.1 적용 전 (롤백 기준)

1. 대상 호스트를 정한다. 분기 시험은 호스트 목록에서 무작위로 고르고 선정 방식을 기록한다.
2. 대상 호스트의 임시 경로 여유 공간이 복원 범위(`/etc`)보다 큰지 확인한다.
3. 롤백은 임시 복원본 삭제다. 시험이 호스트 키 정책이나 저장소를 바꾸지 않으므로 그 밖의 원상복구는 없다.
4. 항목별(대상 호스트, 시험 범위) 운영자 승인을 받는다.

### 3.2 절차

1. root로 `/etc/restic/env`를 환경에 올린 뒤(값은 출력하지 않는다) 저장소 스냅샷 목록을 본다: `resticprofile -f yaml -c /etc/restic/profiles.yaml -n default snapshots`. 호스트의 스냅샷 ID와 시각을 적는다.
2. 임시 경로(`umask 077`)에 `/etc`만 복원한다. **반드시 `--host <스냅샷의 호스트 이름>`으로 거른다**: `... restore latest --host <호스트> --target /tmp/restore-test-<날짜> --include /etc`. 시작과 종료 시각을 적는다.
   - 호스트 이름은 `snapshots`가 보여 주는 값(짧은 이름)이다. `hostname`이 주는 FQDN과 다를 수 있고, 안 맞으면 아무것도 복원되지 않는다.
   - `--host` 없이 `latest`를 쓰면 같은 저장소에 남은 시험 스냅샷이 선택돼 0개 파일이 복원될 수 있다. 복원 요약의 파일 수가 0이면 성공이 아니라 선택 오류다.
3. 원본과 비교한다: `diff -rq /etc /tmp/restore-test-<날짜>/etc`(파일 이름만 출력). 다음은 차이로 치지 않는다.
   - 시험 중 바뀌는 파일(`resolv.conf`, `mtab`, 캐시, `machine-id`)
   - 복원 트리 밖을 가리키는 상대 심볼릭 링크 때문에 나오는 `diff: ... 그런 파일이나 디렉터리가 없습니다`(`localtime`, `os-release`, `grub2.cfg` 등)
   - 백업이 의도적으로 제외하는 `/etc/restic/password`
   - 백업 이후 운영자가 추가·삭제한 파일. 나머지 차이는 설명한다.
4. 임시 복원본을 삭제하고 삭제 사실을 확인한다.
5. 호스트 키는 읽기와 쓰기만 허용하고 `locks/*`만 삭제할 수 있다. `restore`는 `GetObject`만 쓰므로 이 정책으로 성공해야 한다. 정책 때문에 실패하면 [backup-host-key-scope.md](backup-host-key-scope.md) §7의 롤백 트리거로 판단한다.

### 3.3 결과 기록 (비공개 노트, 이슈에는 통과 여부만)

| 항목 | 값 |
|---|---|
| 일시 | |
| 대상 호스트와 선정 방식 | |
| 스냅샷 ID와 시각 | |
| 복원 범위 | |
| 소요 시간(복원, 비교) | |
| 결과(성공·실패) | |
| 차이와 설명 | |
| 임시 복원본 삭제 확인 | |
| 개선 조치 | |

실패하면 개선 조치를 이슈로 등록하고 다음 분기 시험에서 재검증한다. 분기 결과서의 승인은 CISO다.

## 4. 저장소 서버 디스크·RAID 상태

저장소 서버의 디스크·RAID 상태는 Host Agents의 RAID 수집기가 읽는다(`docs/monitoring.md` §3-6). 수집기는 서버에 **이미 있는** HP 관리 도구만 쓴다. 도구가 없는 서버에 설치하려면 [hp-raid-tool.md](hp-raid-tool.md)를 따르고, 설치는 서버마다 사용자 승인을 받는다.

1. 컨트롤러 유무를 읽기 전용으로 확인한다(`ls /sys/bus/pci/drivers/hpsa`, `lspci -nn | grep -i 'smart array'`).
2. 컨트롤러가 없으면 설치 대상이 아니다. 디스크 상태는 SMART 등 다른 수집 방식을 따로 정한다.
3. 컨트롤러가 있고 도구가 없으면 설치를 승인받아 런북대로 설치한다.
4. 다음 수집(5분 안)부터 `host_status_logs`에 `tool_status=ok`와 디스크·RAID 상태가 들어오는지 확인한다.
