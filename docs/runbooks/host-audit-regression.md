# Host Audit 퇴행 점검 적용 런북 (#377, Spec #364)

정기 점검(Host Audit)이 스펙 #364 기대치(관리 웹 접점 루프백, 수신·원격 접속 출발지 제한, 탐지·로그 보존, 백업 정책, 시크릿 파일 권한)를 계속 확인하게 켜는 절차다. 점검은 읽기 전용이고 결과는 항목 ID와 판정뿐이다. 이 저장소는 공개이므로 실제 호스트명·포트·경로·주소·계정은 적지 않는다. 기대치 선언 값, 스냅샷, diff, 승인 기록은 운영자 비공개 경로에 두고 이슈에는 통과 여부만 남긴다. 항목 정의와 합격 기준은 [Host Audit 태스크 명세 16절](../host_audit.md)이 기준이다.

## 1. 전제

- 대상 서버가 Host Audit 점검 범위에 있어야 한다(`host_audit_excluded` 그룹에 없어야 한다). Host Agents 편입은 한쪽 서버에서 보류돼 있다(탐지 복구 런북 전제 3). 범위 밖이면 이 점검은 그 서버를 보지 못하므로 그동안은 수동 절차와 전후 스냅샷 diff로 확인한다.
- 선행 티켓의 조치가 적용돼 있어야 해당 항목이 통과한다. 적용 전에는 해당 선언 키를 넣지 않는다(넣으면 실패로 나오는 것이 정상이다). 기대치별 출처: [관리 웹 접점](mgmt-web-loopback-bind.md), [수신 접점](receiver-source-restriction.md), [SSH 출발지](ssh-source-restriction.md), [탐지 복구](detection-recovery.md), [백업 호스트 키](backup-host-key-scope.md), [시크릿 파일 권한](secret-file-permissions.md).
- 이 점검은 호스트를 바꾸지 않는다. 원격에서 하는 일은 소켓·컨테이너 게시 목록 조회, `sshd -T -C`, `fail2ban-client status`·`get`, `auditctl -l`, `systemctl is-active`, 파일 권한 조회, 설정 파일 읽기뿐이다. 시크릿 파일의 내용은 읽지 않는다.

## 2. 적용 전 (롤백 절차 먼저)

1. **롤백 절차를 적용 전에 적는다**: 롤백은 두 가지다. (a) 해당 호스트의 선언 `host_audit_regression_expect`를 비우면 그 호스트는 이 섹션 대상에서 빠진다. (b) 전체를 끄려면 Extra variables로 `host_audit_regression_enabled=false`를 준다. 어느 쪽도 서버를 건드리지 않는다. 적용 전에 이 두 줄과 선언 원본의 비공개 보관 위치를 노트에 적는다.
2. **기준선 스냅샷**: [보안 기준선 수집기](security-baseline.md)로 대상 서버의 적용 전 스냅샷을 비공개 경로에 남긴다.
   ```bash
   scripts/collect-security-baseline.sh --label <호스트> --ssh <user@host>
   ```
3. **선언 작성**: 비공개 노트에서 호스트별 선언을 작성한다(키는 명세 16.2). 포트·설정 파일 경로·허용 출발지 값은 Semaphore 인벤토리의 호스트 변수나 Environment에 넣고 저장소·이슈에는 쓰지 않는다. 허용 목록에 노드 otelcol OTLP 같은 설계된 모든 주소 청취가 있으면 `mgmt_wildcard_allowed`에 포함한다.
4. 항목군(관리 접점, 수신, SSH, 탐지, 시크릿 권한, 백업 정책)별로 선언을 추가하기 전에 운영자 승인을 받는다. 항목군 하나씩 켠다.

## 3. 적용과 검증

1. 승인된 항목군의 선언을 인벤토리에 넣는다(서버 변경 없음).
2. 수시 실행(`host_audit_run_kind=on_demand`, `target_hosts`로 대상만)으로 Host Audit을 한 번 돈다. 정기 실행이 아니므로 Audit Baseline이 되지 않고 알림도 가지 않는다.
3. 보고서의 Security Regression 절에서 항목별 판정을 본다. **합격 = 선언한 모든 항목이 통과**이고 점검불가는 합격이 아니다. 점검불가 원인(조회 도구 없음, 권한)을 먼저 해소한다.
4. 같은 명령으로 **적용 후 스냅샷**을 만들어 2절의 스냅샷과 diff한다. 읽기 전용 점검이므로 방화벽·열린 접점·sshd·로그 저장·권한 구간 모두 diff가 비어야 한다. 달라졌다면 점검과 무관한 변경이므로 원인을 확인한다.
   ```bash
   scripts/collect-security-baseline.sh --label <호스트>-after-377 --ssh <user@host>
   ```
5. 백업 정책 항목(`EXP-BAK-*`)을 쓰려면 읽기 전용 수집기로 스냅샷을 만들고 그 파일을 러너 경로로 지정한다(`HOST_AUDIT_RUSTFS_POLICY_SNAPSHOT`). 점검 계정은 서버 정책을 직접 읽지 않는다(최소 권한). 스냅샷이 오래되면 판정도 그 시점 기준이므로 실행 직전에 만든다.
   ```bash
   scripts/collect-rustfs-policy.py --label <저장소 서버> --env-file <저장소 루트 .env>
   ```
   변수 `host_audit_regression_backup_enabled=true`로 켠다.
6. 통과 여부만 이슈에 적는다. 보고서·스냅샷·diff 원본은 비공개 경로에 둔다.

## 4. 부정 시험 (운영 서버를 퇴행시키지 않는다)

- 퇴행 시 실패로 보고되는지는 시험 환경에서 증명한다: 프로브 단위 시험(`tests/test_host_audit_regression_probe.py`)과 Molecule Fast Scenario의 `VERIFY-AUD-701`이 항목별로 의도적 퇴행을 만들어 실패를 확인한다. 운영 서버에서는 일부러 설정을 되돌려 시험하지 않는다.
- 운영 서버에서 확인할 수 있는 부정 시험은 읽기 전용이다: 허용 밖 출발지가 거부되는지(`EXP-SSH-2`)는 점검이 `sshd -T -C`로 평가한 결과로 판정되며, 실제 접속 시험은 각 런북의 부정 시험 절차를 따른다(시험 출발지는 비공개 경로에 지정).

## 5. 퇴행 알림

- 정기 실행에서 지난 정기 점검에 실패가 아니던 항목이 이번에 실패하면 기존 KISA 악화 알림과 같은 경로로 항목 ID와 호스트 이름이 알림 본문에 들어간다. 주소·포트·값은 들어가지 않는다. 알림은 [알림 런북](alerts.md)의 대응 절차와 같이 처리한다.
- 처음 선언한 호스트와 첫 정기 실행은 비교 대상이 없어 알림이 가지 않는다. 이 기간에는 보고서의 실패 목록이 유일한 신호이므로 선언 직후 첫 정기 실행 보고서를 직접 확인한다.
- 실패의 원인이 의도한 변경이면 선언을 고치거나 해당 항목군의 선언을 내리고 그 결정을 비공개 노트에 남긴다. 아니면 해당 런북의 조치를 다시 적용한다.

## 6. 체크리스트

- [ ] 적용 전 기준선 스냅샷(비공개)
- [ ] 항목군별 운영자 승인
- [ ] 선언 추가, 수시 실행, 모든 선언 항목 통과(점검불가 없음)
- [ ] 적용 후 같은 명령 스냅샷 diff가 빔
- [ ] 이슈에는 통과 여부만 기록
