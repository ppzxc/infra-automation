# 시크릿 파일 권한 정렬·평문 정리·잔재 정리 런북 (#375, Spec #364)

핵심 서버의 시크릿 파일 권한을 AGENTS.md 규칙에 맞추고, 설정 파일의 평문 인증 정보와 오래된 잔재를 정리한다. 이 저장소는 공개이므로 실제 호스트명·경로·IP·계정·값은 적지 않는다. 소비자 목록, 스냅샷, diff, 승인 기록은 모두 운영자 비공개 경로에 두고 이슈에는 통과 여부만 남긴다. 권한만 바꾸고 파일 내용은 읽지 않는다.

## 전제

- 평문 인증 정보를 정리(수정·삭제)하기 전에 원본 사본을 먼저 만들어 #374의 보관 대상(로컬 암호 관리 도구)에 포함시킨다. 보관이 끝났다는 #374의 확인이 없으면 평문 정리 단계로 가지 않는다.
- 적용 전 기준선 스냅샷은 `scripts/collect-security-baseline.sh`([보안 기준선 런북](security-baseline.md))로, 권한 목록은 `scripts/collect-secret-perms.sh`로 만든다. 적용 후 같은 명령으로 다시 만들어 diff한다.
- 모든 변경은 항목별로 설계 보고 후 운영자 승인을 받아 적용한다. 승인 없이 한 번에 일괄 적용하지 않는다.
- 시크릿 저장소(OpenBao)와 Semaphore 스택은 운영자만 정해진 재기동 절차로 다룬다. 이 런북의 어떤 단계도 그 스택을 `up`·재생성하지 않는다.

## 1. 소비자 목록 만들기

권한을 바꾸기 전에 파일별로 "누가 어떤 경로로 읽는지"를 먼저 적는다. 목록은 비공개 경로에 둔다.

양식(파일 한 개당 한 줄):

| 파일(비공개 경로 기준) | 현재 mode owner:group | 소비자 | 읽는 경로 | 목표 mode owner:group | 근거 | 확인 방법 |
|---|---|---|---|---|---|---|
| (파일) | (수집 결과) | (서비스·사용자) | env_file / bind mount / root 전용 | (아래 분류) | (분류 규칙) | (아래 3절) |

분류 규칙:

1. **compose `env_file:`로 읽는 파일 -> `0640 root:dockermgmt`.** compose는 `env_file:`을 실행한 사용자 권한으로 읽는다. 실행 주체는 `docker` 그룹의 개인 운영자 계정이므로 `0600 root`로 좁히면 `docker compose config`가 읽기 거부로 실패한다. 이 예외는 소비자별로 나눈 시크릿 env 파일에만 적용한다(AGENTS.md 4절 예외, ADR-0002 개정).
2. **컨테이너가 bind mount로 직접 읽는 파일 -> 컨테이너 내부 UID로 읽을 수 있는지 먼저 확인한다.** 호스트 mode가 아니라 컨테이너 안의 프로세스 UID(이미지 설정의 `USER`나 compose의 `user:`)가 소유자나 그룹으로 읽을 수 있어야 한다. 확인 전에는 목표 mode를 정하지 않는다. 소유자를 컨테이너 UID로 맞추는 경우에도 mode는 `0600` 이하를 우선한다.
3. **systemd나 root 전용 스크립트만 읽는 파일 -> `0600 root:root`.** 다른 소비자가 없다는 것을 소비자 목록에서 확인한 뒤에만 좁힌다.
4. 분류가 불확실한 파일은 바꾸지 않고 목록에 "미정"으로 남겨 운영자가 정한다.

## 2. 적용 전 준비

1. 기준선 스냅샷과 권한 목록을 수집해 비공개 경로에 저장한다(같은 명령을 적용 후에도 쓴다).
   ```bash
   scripts/collect-security-baseline.sh --label <호스트> --ssh <계정>@<호스트>
   ssh <계정>@<호스트> 'sudo -n bash -s' < scripts/collect-secret-perms.sh > <비공개 경로>/secret-perms-before.txt
   ```
2. **롤백 절차를 적용 전에 적는다.** `secret-perms-before.txt`의 `mode owner:group path` 줄이 롤백 기준이다. 되돌릴 때는 파일마다 기록된 값으로 `chmod`·`chown`을 되돌린다(적용 전 스냅샷 값을 그대로 쓴다). 롤백 명령 목록을 승인 요청에 함께 첨부한다.
3. `docker compose config --quiet`를 대상 호스트의 compose 버전이 지원하는지 먼저 확인한다(`docker compose version`과 `docker compose config --help`). 지원하지 않으면 이 런북의 3절 판정을 쓸 수 없으므로 운영자에게 보고하고 대체 확인 수단을 승인받는다.
4. 목록의 항목별로 운영자 승인을 받는다.

## 3. 권한 변경과 판정

항목별로 승인된 것만 `chmod`·`chown`으로 바꾼다. 파일 내용은 열지 않는다.

판정은 **개인 운영자 계정**(compose를 실제로 실행하는 계정)으로, 해당 compose 프로젝트 디렉터리에서 종료 코드만 본다.

```bash
docker compose config --quiet; echo "exit=$?"
```

- `exit=0`이면 `env_file:` 읽기가 정상이다. 0이 아니면 읽기 거부나 설정 오류이므로 즉시 해당 항목을 롤백한다.
- `--quiet`는 해석 결과를 출력하지 않는다. 값이 화면이나 로그에 나오는 `docker compose config`(옵션 없음)와 `env` 출력은 쓰지 않는다.
- **`docker compose up`, `restart`, `--force-recreate`는 확인 수단으로 쓰지 않는다.** 컨테이너를 재생성하면 시크릿 저장소 스택처럼 운영자 키 입력이 필요한 서비스가 죽는다. 시크릿 저장소·Semaphore 스택의 재기동이 필요하면 운영자가 정해진 재기동 절차로 직접 한다.
- bind mount 파일은 컨테이너를 건드리지 않고 UID 읽기 가능 여부만 호스트에서 확인한다(소유자·그룹·mode와 컨테이너 UID 대조). 실제 컨테이너 재기동은 운영자가 승인하는 별도 작업이다.

## 4. 평문 인증 정보 정리

1. 수집기의 `plaintext-credential-files` 구간(경로만 나옴)을 후보 목록으로 쓴다. 후보일 뿐이므로 운영자가 직접 확인한다.
2. **정리 전에 해당 파일의 사본을 #374 보관 대상에 포함한다.** 사본은 비공개 경로를 거쳐 로컬 암호 관리 도구로만 옮기고 저장소에 두지 않는다.
3. 값은 `${VAR}` 참조나 시크릿 저장소 조회로 바꾼다(AGENTS.md 4절). 파일별로 승인 후 적용하고, 적용 후 3절의 판정을 다시 돌린다.

## 5. 셸 이력 후보

- 수집기는 이력 파일의 위치와 시크릿 후보 줄 수만 보고한다(`shell-history-candidates` 구간). 줄 내용은 출력·저장하지 않는다.
- 이력 안의 값이 실제 시크릿인지, 교체할 것인지는 **운영자가 직접 이력을 보고 정한다.** 도구는 교체를 결정하지 않는다.
- 이력 파일을 지우거나 줄이는 작업도 항목별 승인 대상이다.

## 6. 잔재 정리(오래된 도구·이미지·옛 이름)

1. 먼저 읽기 전용으로 목록을 만든다: 미사용 컨테이너 이미지, 더 이상 쓰지 않는 도구와 디렉터리, 옛 이름의 설정·계정·백업 잔재.
2. 목록의 **항목별로 운영자 승인**을 받은 것만 삭제한다. 묶음 승인·`prune` 일괄 삭제는 쓰지 않는다.
3. 삭제 전에 되돌릴 방법(이미지는 태그와 ID 기록, 파일은 사본 위치)을 목록에 적는다. 인증 정보가 든 파일이면 4절의 사본 규칙을 먼저 따른다.
4. 삭제 후 기준선 스냅샷을 다시 만들어 diff에 의도한 변화만 있는지 확인한다.

## 7. 컨테이너 이미지 고정 버전 목록

이미지 상향은 이번 범위가 아니다. 현재 쓰는 버전을 고정 목록으로 남기고 갱신 계획의 근거로 쓴다. 목록은 비공개 경로에 두고 이슈에는 작성 완료 여부만 적는다.

양식:

| 호스트 | 컨테이너(프로젝트-서비스) | 이미지:태그 | 이미지 ID(앞 12자) | 이미지 생성일 | 고정 여부(태그/다이제스트) | 갱신 계획 |
|---|---|---|---|---|---|---|
| (호스트) | (이름) | (repo:tag) | (ID) | (날짜) | (예: 태그만, `latest` 아님) | (후속 패치 티켓 또는 보류 사유) |

- 수집은 기준선 스냅샷의 `container-images`·`published-containers` 구간을 쓴다.
- `latest`처럼 움직이는 태그는 고정 여부 칸에 표시하고 갱신 계획에 근거를 적는다.

## 8. 적용 후 검증과 기록

1. 같은 명령으로 적용 후 스냅샷을 만들고 diff한다. diff에는 승인된 항목의 변화만 있어야 한다.
   ```bash
   ssh <계정>@<호스트> 'sudo -n bash -s' < scripts/collect-secret-perms.sh > <비공개 경로>/secret-perms-after.txt
   diff <비공개 경로>/secret-perms-before.txt <비공개 경로>/secret-perms-after.txt
   ```
2. 수집기의 `too-open-candidates` 구간이 비어 있어야 한다.
3. 부정 시험: `0640 root:dockermgmt` 파일을 `dockermgmt` 그룹이 아닌 일반 계정으로 읽으려 하면 거부돼야 한다(시험 계정은 비공개 경로에 지정, 값은 출력하지 않고 종료 코드만 본다).
4. 3절의 `docker compose config --quiet` 종료 코드가 항목별로 0이어야 한다.
5. 이슈에는 통과 여부만 적는다(스냅샷·diff·소비자 목록 원본은 올리지 않는다).
6. Host Audit 퇴행 점검은 이 런북의 시크릿 파일 권한 기준을 `EXP-SEC-1`~`EXP-SEC-3`으로 이어받는다([Host Audit 명세 16절](../host_audit.md)). 평문 후보 경로 점검은 #374 선행 때문에 이번 항목에 넣지 않았다.
