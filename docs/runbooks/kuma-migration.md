# Uptime Kuma 이전 절차와 모니터 운영 규칙 (#394)

Uptime Kuma를 다른 서버로 옮길 때의 절차와 이전 뒤 모니터가 실패하는 원인, 모니터 이름·심각도·알림 제목 규칙을 적는다. 공개 저장소이므로 주소·포트·출발지·토큰은 적지 않는다. 구체값은 비공개 경로에 둔다.

이 Kuma는 별도 DB 컨테이너 없이 **내장 MariaDB**(`embedded-mariadb`)를 쓴다. 데이터는 마운트한 데이터 디렉터리 안의 `mariadb/`에 있다.

## 이전 절차

1. 옛 서버에서 Kuma를 **정상 종료**한다. 내장 MariaDB가 내려갈 시간이 필요하므로 `docker stop -t 120`을 쓰고 로그에 종료 완료가 찍혔는지 확인한다. 가동 중에 압축하면 InnoDB가 서로 다른 시점의 파일을 묶게 된다.
2. 컨테이너가 멈춘 상태에서 데이터 디렉터리를 `tar --numeric-owner -p`로 압축한다.
3. 새 서버에서 **root 권한으로** 풀어 소유자를 보존한다. 일반 계정으로 풀면 파일이 그 계정 소유가 되어 컨테이너 안의 MariaDB(사용자 uid 1000)가 쓰지 못하고 기동이 실패한다. 풀린 뒤 `mariadb/` 안 파일의 소유자가 uid 1000인지 확인한다.
4. 새 서버의 compose로 기동하고 로그에서 `Embedded MariaDB is ready for connections`와 `Connected to the database`를 확인한다.
5. 이미 일반 계정으로 풀어 버렸다면, 복구 전에 현재 상태를 복사해 두고(`cp -a`) 데이터 디렉터리를 uid 1000으로 `chown -R`한 뒤 남은 `mysqld.pid`를 지우고 기동한다. 가동 중에 압축한 흔적은 InnoDB crash recovery가 자동으로 정리한다(로그의 recover 페이지 수를 확인).

## 이전 뒤 모니터가 실패하는 원인

새 Kuma 서버의 출발지가 바뀌므로 세 곳을 점검한다.

| 증상 | 원인 | 조치 |
|---|---|---|
| HTTP 모니터가 401 | 감시 대상 프록시의 프로브 경로(`/healthz`, `/healthz/app`)는 허용 출발지 목록에 든 곳에서만 응답한다 | 목록에 새 Kuma 서버를 추가하고 프록시 컨테이너를 **재생성**한다(환경변수라 reload로 반영되지 않는다). 대기 노드부터 한 대씩 적용한다 |
| push 모니터가 DOWN 고정 | 호스트 cron이 옛 Kuma 주소로 push한다. push 토큰은 DB와 함께 이전되므로 호스트에서는 주소의 호스트명만 바꾸면 된다 | cron의 주소를 새 Kuma로 바꾸고 토큰이 새 DB와 같은지(해시로) 비교한다 |
| push가 404 | 새 Kuma 서버 ingress의 허용 목록이 호스트 출발지를 막는다(404는 Kuma가 아니라 ingress가 낸 것) | 허용 목록에 노드 출발지를 추가한다. 단일 파일 bind mount이므로 `sed -i`가 아니라 `>>`로 붙이고 reload한다 |

서버가 자기 공인 도메인으로 직접 부르면 ingress는 출발지를 컨테이너 네트워크 게이트웨이로 본다. 자기 호스트에서의 404는 장애가 아니다.

## 사설망 감시: push 전환

새 Kuma 서버가 사설망에 닿지 않으면 사설 주소로 직접 접속하는 모니터(redis 등)는 시간 초과가 난다. 이럴 때는 **호스트가 사설망 안에서 확인하고 결과를 push**하도록 바꾼다.

- 스크립트가 서비스 상태를 확인하고 `status=up|down`으로 push URL을 호출한다. 서비스 비밀번호는 실행 때 설정 파일에서 읽어 환경변수로만 넘기고 cron·로그·프로세스 목록에 남기지 않는다.
- 기존 모니터를 `push` 타입으로 변환하면 지난 하트비트 이력이 유지된다. 변환할 때 접속 문자열(비밀번호 포함)은 비운다.
- **interval은 보내는 주기의 1.5배 이상으로 잡는다.** 같게 두면 "시간 창 안에 하트비트 없음"(DOWN)과 도착한 push(UP)가 같은 초에 번갈아 기록되어 알림이 왔다 갔다 한다(60초/60초에서 재현, 90초로 해결).
- 한계: 호스트나 cron이 멈추면 서비스 이상과 구분되지 않고 DOWN으로 보인다.
- Kuma DB를 직접 고쳤다면 반영을 위해 Kuma를 재시작한다(`docker stop -t 120` 후 시작).

## 모니터 이름·심각도·알림 제목

- 이름은 `<대상> <구성요소>`로 통일한다. 예: `ns0327 app`, `ns0327 valkey-master`. 대상이 호스트가 아닌 VIP 도메인이면 도메인을 그대로 쓰고 구성요소를 붙인다(`funa.nanoit.kr vip`). 공인·내부 도메인 구분은 이름이 아니라 태그에 둔다.
- 심각도는 태그 `P1`·`P2`·`P3`로 붙인다. 태그가 없으면 P3으로 취급한다. 서비스 영향이 곧바로 나는 `app`·`caddy`·`valkey-master`·VIP는 P1, 이중화가 있는 `valkey-replica`와 `keepalived`는 P2다.
- 알림 제목은 `🔴|✅ [심각도] <이름> 다운|복구`, 본문은 OpenObserve 알림과 같은 `■ 현상`, `■ 대상`, `■ 발생 시각` 형식이다(`docs/openobserve_config.md`의 알림 메시지 규칙). 템플릿은 Kuma 알림 채널의 사용자 지정 본문(Liquid)에서 `monitorJSON.tags`로 태그를 읽는다.
- push 모니터는 대상 주소가 의미 없는 값이라 `■ 대상` 줄을 뺀다.

## 점검 항목

- 모든 모니터에 알림 채널이 연결되어 있는지 확인한다(연결이 빠진 모니터는 장애가 나도 알림이 가지 않는다).
- 이름 규칙과 심각도 태그가 모든 모니터에 있는지 확인한다.
- Kuma의 모니터·태그·알림 템플릿은 공식 쓰기 API가 없어 이 저장소에서 코드로 관리하지 않는다(ADR-0010). 변경 전 DB 덤프(`mariadb-dump --single-transaction`)를 받아 둔다.

## 롤백

- 이전 전 사본을 보관한다(`cp -a`한 데이터 디렉터리 또는 DB 덤프). 문제가 있으면 Kuma를 정상 종료하고 사본을 uid 1000 소유로 복원한 뒤 기동한다.
- 호스트 쪽 변경(프록시 `.env`, crontab, push 스크립트)은 변경 전 파일을 같은 위치에 날짜 접미사로 남겨 두고 되돌린다. 프록시 `.env`를 되돌릴 때도 컨테이너 재생성이 필요하다.

수동으로 바꾼 호스트 설정을 이 저장소의 역할로 옮기는 일은 #395에서 다룬다.
