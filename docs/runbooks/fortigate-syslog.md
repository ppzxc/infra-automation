# 포티게이트 방화벽 로그 수신 런북

> 포티게이트 방화벽(IDC HA 2대 멤버, 사무실 1대)의 ISMS 증적 로그가 OpenObserve `security_logs`까지 가는 경로, 장비 쪽 거름 기준, 점검 절차다(Spec #282 / #283). 수신 경로는 [스위치 syslog 런북](switch-syslog.md)을 재사용한다. 공개 저장소라 IP·포트·장비 명령과 값은 적지 않으며, 장비에서 사람이 하는 설정의 체크리스트는 담당자의 로컬 비공개 자료에 있다.

## 1. 경로

```text
방화벽 ──syslog(TCP, 구조화 형식)──▶ syslog-ng 컨테이너 ──▶ 장비별·일별 파일 ──▶ 호스트 otelcol(filelog) ──▶ OpenObserve security_logs
```

| 구간 | 내용 |
|---|---|
| 수신 | 스위치와 같은 syslog-ng 컨테이너가 받는다. 수신 허용 목록에 방화벽 출발지를 등록해야 한다(2절 HA 멤버 구성). |
| 파일 보관 | `/var/log/remote/fortigate/<송신 장비>/<날짜>.log`. **스위치 파일(`/var/log/remote/<송신 장비>/`)보다 한 단계 깊은 경로**에 써서 스위치용 수집 경로(`/var/log/remote/*/*.log`)가 방화벽 줄을 한 번 더 읽어 `system_logs`에 중복 수집하지 않게 한다. 호스트 logrotate 보관 기간은 스위치와 같다. |
| 중앙 수집 | 호스트 KV `otel_extra_logs`에 `path=/var/log/remote/fortigate/*/*.log`, `stream=security_logs`, `service=fortigate-syslog`를 더한다. 절차와 KV 주의는 스위치 런북 2절과 같다(PATCH 불가, 전체를 읽어 합쳐 `cas`, 값 출력 금지). 코드 변경은 필요 없다. |
| 분류·보관 | `security_logs`. 스위치(`system_logs`, `switch-syslog`)와 서비스 이름으로 구분한다. 보관은 서버 전역 365일(ISMS 로그 1년). |
| 중앙 변환 | 추가 경로에는 파서가 적용되지 않는다(ADR-0006 §2.3). 원문은 그대로 저장되고 `security_semantics` 함수는 이 레코드를 건드리지 않는다. 대신 같은 보안 로그 파이프라인의 다음 함수 `fortigate_semantics`가 `fortigate-syslog` 레코드에만 장비(`device_name`, 관리번호 `device_id`)·유형·하위 유형·동작·출발지·사용자·정책 식별자 필드를 **추가**한다(필드 표는 [OpenObserve 구성](../openobserve_config.md), ADR-0008, Spec #282 / Ticket-2). 해석할 수 없는 줄은 그대로 통과한다. |

장비 구분은 파일 경로 속성과 원문의 장비 이름으로 한다. 두 HA 멤버가 서로 다른 장비 이름을 가져야 검색에서 구분된다.

## 2. 장비 쪽 로그 거름 기준

거름은 장비 쪽에서 1차로 한다. 핵심은 장비 전역 필터가 아니라 **정책별 로그 설정**이다.

| 구분 | 대상 |
|---|---|
| 수집(포함) | 관리자 접속·로그인 성공/실패, 설정·정책·계정·권한 변경, HA 전환·재부팅·인터페이스 이벤트, VPN 접속, UTM 탐지·차단(IPS·AV·웹필터), 정책 거부 트래픽, 장비 자체 접속 거부 |
| 제외 | 허용(accept) 트래픽 전체, 멀티캐스트, 스니퍼, 음성 로그 |
| 예외 | 허용 정책 중 중요 구간(예: DMZ에서 내부망)만 정책 단위로 로그를 켠다. 대상 정책 목록은 비공개 자료에 둔다 |

- 정책별 로그 설정 원칙: 허용 정책은 기본 로그 끔, 중요 구간만 켬. 맨 아래에 **로그를 켠 명시적 거부 정책**을 둔다(암묵적 거부는 로그가 남지 않는다).
- 새 정책을 만들 때 이 기준으로 로그 설정을 정한다.
- 전송은 신뢰성 있는 전송(TCP)과 구조화된 syslog 형식, 고정된 출발지 주소를 쓴다. 정확한 명령과 값은 FortiOS 버전마다 다르므로 사용 중인 버전 문서로 확인하고 비공개 자료에만 적는다.

### 대상 장비와 FortiOS 버전

| 장비 이름(관리번호) | 위치·역할 | 모델 / FortiOS |
|---|---|---|
| `ns0380`, `ns0381` | IDC 외부/내부 경계 Active-Passive HA 쌍 | FortiGate 70G / 7.2.13 |
| `ns0399` | 사무실 | FortiGate 60F / 7.4.12 |

- 장비 이름은 관리번호(소문자, 인벤토리 호스트명)를 쓴다. 버전이 7.2와 7.4로 둘이라 명령과 항목 이름이 다를 수 있으므로 각 버전의 공식 문서로 확인하고, 확신이 없는 명령은 비공개 체크리스트에서 확인한 값만 쓴다.
- 현재 장비 쪽 syslog 설정은 **아직 하지 않았다.** 적용 순서는 사무실(`ns0399`)을 먼저 적용해 실제 로그 샘플을 확보한 뒤 IDC 쌍에 적용한다. 샘플이 있어야 필드 추출을 확정한다(5절).

### HA 멤버 구성

- Active-Passive HA의 설정은 멤버 간 동기화되지만 장비 이름(hostname)은 멤버별로 따로 둘 수 있다. **두 멤버의 hostname을 서로 다르게(`ns0380`, `ns0381`) 한다.**
- IDC 쌍은 **HA 관리 인터페이스를 쓸 수 없고** 두 멤버가 같은 주소로 접근된다. 로그는 그 시점의 primary가 보낸다. 장애 전환 뒤에는 새 primary가 같은 출발지로 보내므로 **멤버 구분은 출발지가 아니라 원문의 hostname(장비 이름)으로 한다.**
- **한계(수용 위험)**: 현재 구성에서는 secondary에 직접 접속한 이력과 secondary가 로컬로 남기는 이벤트 로그를 중앙에서 직접 수집할 수 없다. HA 관리 인터페이스를 쓸 수 있게 되면 멤버별 전송으로 바꾼다. 공식 문서(7.2)로 확인된 대안이 있으면 비공개 체크리스트에 근거와 함께 적고 확인된 뒤에만 이 절에 반영한다.
- syslog-ng 수신 허용 목록은 **IDC 출발지 1개 + 사무실 1개**(S2S 경로에서 변환된 출발지)다. 값은 비공개 자료에 둔다.

## 3. 점검 절차

1. **장비 설정**: 비공개 체크리스트로 로그 전송(대상, 형식, 출발지 고정), 정책별 로그 설정, HA 관리 인터페이스를 확인한다.
2. **허용 목록**: syslog-ng 수신 허용 목록에 IDC 출발지 1개와 사무실 변환 출발지 1개가 있는지 본다.
3. **수신**: syslog-ng 통계에서 처리 건수가 늘어나는지 본다(방화벽은 로그가 계속 나오므로 멈추면 바로 보인다). 늘지 않으면 장비 전송 설정, 허용 목록, 경로를 순서대로 본다.
4. **파일**: `/var/log/remote/fortigate/` 아래에 장비별 디렉터리와 오늘 날짜 파일이 생기는지 본다. 스위치 경로와 같은 단계에 방화벽 디렉터리가 생겼다면 설정이 틀린 것이다(중복 수집 위험).
5. **OpenObserve**: `security_logs`에서 `service_name='fortigate-syslog'`의 최신 시각을 장비 이름별로 본다. IDC 두 멤버(`ns0380`, `ns0381`, 장애 전환 뒤에는 새 primary 이름)와 사무실(`ns0399`)이 보여야 한다. 평소에는 primary 이름만 보일 수 있다. 없으면 호스트 otelcol 설정에 경로가 있는지와 서비스 상태를 본다.
6. **거름 확인**: 허용 트래픽이 섞여 들어오지 않는지(건수가 비정상적으로 많지 않은지), 관리자 로그인 시도·정책 거부가 들어오는지 확인한다.
7. **secondary 직접 접속**: 현재 구성에서는 중앙에 남지 않는 것이 정상이다(2절 한계). 장애 전환 시험을 한 경우 새 primary 이름으로 로그가 이어지는지만 본다.
8. **다른 경로 영향 없음**: 같은 시각의 `switch-syslog`, 서버 로그가 평소대로 들어오는지 본다.

## 4. 신규 방화벽 편입 절차

1. 장비 이름을 고유하게 정한다(HA는 멤버마다 다른 hostname). 관리번호 규칙은 CONTEXT.md의 Inventory Hostname을 따른다.
2. 비공개 체크리스트에 장비 항목을 더하고 로그 전송과 정책별 로그 설정을 적용한다.
3. syslog-ng 수신 허용 목록에 출발지(HA 쌍은 공통 출발지 1개)를 더하고 `syslog-ng-ctl reload`로 설정만 다시 읽힌다.
4. 3절의 점검 절차로 파일 생성과 `security_logs` 도착을 확인한다.
5. 수신 중단 감시 목록, 설정 백업 대상 등 후속 티켓의 목록에 더한다(해당 기능이 반영된 뒤).
6. 비공개 체크리스트에 완료 일자를 적는다.

## 5. 알려진 한계

- 원문 시각의 시간대는 장비 설정에 의존한다. 증적 기준 시각은 수집 시각이다.
- **필드 추출은 합성 입력으로만 검증됐다.** `fortigate_semantics`와 그 테스트(`tests/test_openobserve_vrl.py`)는 FortiOS 7.2/7.4 Log Message Reference의 기본 key=value 형식으로 만든 가짜 줄을 쓴다. 사무실 장비(`ns0399`)의 실제 로그 샘플(비공개 경로)을 받으면 키 이름(`devname`, `type`, `subtype`, `action`, `srcip`, `remip`, `ui`, `user`, `policyid`)과 값 모양(따옴표, `N/A`, 관리자 접속 줄의 주소 위치)을 대조해 규칙과 테스트를 고친다. 그 전에는 `security_logs`에서 `device_id`·`event_action` 등이 비어 있는 줄이 있을 수 있다.
- 알림, 수신 중단 감시, 설정 백업은 이 런북의 범위 밖이다(Spec #282의 다른 티켓).
- 허용 트래픽은 수집하지 않으므로 "허용된 접속이 있었는지"는 이 로그로 증명되지 않는다. 중요 구간만 정책별로 켠 범위에서만 남는다.
