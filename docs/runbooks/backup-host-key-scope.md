# 백업 호스트 키 삭제 권한 축소 런북 (#373, Spec #364 / Ticket-6)

호스트 백업 서비스 계정(호스트 키)의 정책을 "쓰기 + 잠금 해제용 삭제"로 한정해, 호스트가 침해돼도 스냅샷 데이터가 지워지지 않게 한다. 정리(`forget --prune`)와 검사(`check`)는 중앙 유지보수 키가 이미 하므로 그대로 둔다. 카나리 호스트 1대에서 먼저 시험한 뒤 전체로 넓힌다. 정책 서술의 출처는 [`roles/backup/files/host-key-policy.json`](../../roles/backup/files/host-key-policy.json) 하나다([backup.md](../backup.md) §2.5, [ADR-0006](../adr/0006-host-agents-otelcol-resticprofile.md) §2.5가 이 파일을 가리킨다).

공개 저장소이므로 주소·포트·접근키·출발지는 이 문서에 쓰지 않는다. 기록은 모두 비공개 경로(`~/.local/share/infra-automation/sec-review-20261026/`)에 두고 이슈에는 통과 여부만 적는다.

## 1. 정책과 한계

| 대상 | 허용 | 근거 |
|---|---|---|
| 버킷 | `s3:ListBucket`, `s3:GetBucketLocation`, `s3:ListBucketMultipartUploads` | restic이 저장소 존재 확인과 목록에 씀 |
| 버킷 안 객체 | `s3:GetObject`, `s3:PutObject`, `s3:AbortMultipartUpload`, `s3:ListMultipartUploadParts` | 백업 쓰기. 멀티파트 중단은 올린 조각의 정리이지 스냅샷 삭제가 아님 |
| `locks/*` | `s3:DeleteObject` | restic `backup`이 끝에 자기 잠금을 지우고 `unlock`이 오래된 잠금을 지움 |

- `${BUCKET}`은 호스트 버킷 이름(`backup-prod-<호스트>`)으로 바꿔 서비스 계정에 적용한다. 저장소는 버킷 루트에 있으므로 잠금 위치는 `<버킷>/locks/*`다.
- 서비스 계정 정책은 부모 계정 권한과의 교집합으로 동작한다. 부모가 넓은 권한이어도 호스트 키는 이 정책 안으로 제한된다.
- 알려진 한계: `PutObject`가 있어 호스트 키는 기존 객체를 같은 이름으로 덮어쓸 수 있다. 삭제는 막지만 변조는 막지 못한다. 중앙 `check`(매월 `--read-data-subset`)가 손상을 탐지하고, Object Lock은 RustFS 제약으로 쓸 수 없다.
- 정책을 넓히는 변경은 정책 파일, 문서, 테스트(`tests/test_backup_host_key_policy.py`), 가드 태스크 `BAK-220`을 함께 바꿔야 통과한다.

## 2. 적용 전 준비 (승인 항목)

1. 기준선 스냅샷: `scripts/collect-rustfs-policy.py --label <백업 저장소 라벨> --env-file <저장소 루트 .env>`로 사용자·그룹·서비스 계정·정책을 수집해 비공개 경로에 남긴다(`rustfs-policy.txt`). 적용 후 같은 명령으로 다시 수집해 `diff`한다.
2. 롤백 기준: 위 스냅샷의 대상 서비스 계정 정책 줄이 되돌릴 값이다(현재 호스트 버킷 전체에 대한 모든 동작 허용). 호스트 키 접근키·비밀키는 바꾸지 않는다(정책만 교체).
3. 카나리 호스트 선정: 중앙 유지보수 대상이고(`host_agents_excluded` 아님), 최근 Deploy와 백업이 연속 성공했으며, 접속 경로가 안정적인 호스트 1대. 선정 결과와 근거는 비공개 노트에 적고 운영자가 승인한다.
4. 카나리 호스트의 마지막 백업 이벤트(`backup_logs`의 `job=backup`)가 성공이고 중앙 유지보수 직전 실행이 성공인지 확인한다.
5. 항목별(카나리, 전체 확대) 운영자 승인을 받는다. 승인 없이 적용하지 않는다.

## 3. 카나리 적용

1. 정책 파일의 `${BUCKET}`을 카나리 호스트 버킷 이름으로 바꾼 사본을 비공개 경로에 만든다(저장소 파일은 바꾸지 않는다).
2. RustFS 관리 콘솔 또는 관리 API(운영자 권한)에서 카나리 호스트 서비스 계정의 session policy를 그 사본으로 교체한다. 접근키는 그대로 둔다.
3. 적용 직후 같은 수집기로 스냅샷을 만들어 기준선과 `diff`한다. 바뀐 줄은 카나리 서비스 계정 정책 하나뿐이어야 한다.

## 4. 카나리 검증

모든 시험은 **임시 시험 객체**만 쓴다. 실제 스냅샷 데이터에 삭제를 시도하지 않는다. 호스트 키는 카나리 호스트의 환경 파일(`backup_env_path`, 0600)에서 root가 읽어 쓰고, 값은 출력하지 않는다. 엔드포인트와 버킷은 비공개 노트의 값을 쓴다.

| # | 시험 | 기대 결과 |
|---|---|---|
| 1 | 호스트 키로 버킷 안 임시 객체 `zz-policy-probe/<시각>` 업로드 | 성공 |
| 2 | 호스트 키로 위 객체 삭제 | **거부**(AccessDenied 계열, 종료 코드 비0) |
| 3 | 호스트 키로 `locks/zz-policy-probe-<시각>` 업로드 후 삭제 | 둘 다 성공 |
| 4 | 카나리 호스트에서 수동 백업(`systemctl start host-agents-backup` 또는 `/etc/cron.d`의 같은 명령) | 성공, `backup_logs`에 `job=backup` `success=true` |
| 5 | 중단된 잠금 정리: `restic unlock`(호스트 쪽 같은 환경) | 성공(잠금 삭제만 일어남) |
| 6 | 중앙 유지보수: Semaphore "Host Agents — Repo Maintenance"를 `-e target_hosts=<카나리> -e backup_maintenance_read_subset=always`로 실행 | `check`, `check --read-data-subset`, `forget --prune` 모두 성공 |

- 시험 2의 거부를 확인한 뒤 시험 1의 잔여 객체는 중앙 유지보수 키(운영자)로 지운다. 호스트 키로는 지워지지 않는 것이 정상이다.
- 시험 6이 실패하면 확대하지 않는다. 유지보수 키는 호스트 키와 별개이므로 실패 원인은 유지보수 키 정책·네트워크·restic 잠금에서 찾는다.
- 카나리 확인 후 24시간(백업 주기 1회)을 지켜보고 다음 백업이 성공하는지 확인한다.

## 5. 전체 확대

1. 카나리가 통과하면 운영자 승인을 받고, 대상 호스트 목록을 비공개 노트에 만든다(분할 순서 권장: 소수 묶음 단위).
2. 호스트마다 3절 절차로 정책을 교체한다. 교체 때마다 시험 2, 3, 4(수동 백업)를 같은 방식으로 확인한다.
3. 마지막 호스트까지 끝나면 수집기로 최종 스냅샷을 만들어 기준선과 `diff`한다. 모든 `backup-prod-*` 서비스 계정이 같은 정책 모양이어야 한다.
4. **확대 후 첫 백업 주기(02:00~03:59 창)가 지난 뒤** `backup_logs`에서 모든 호스트의 `job=backup`이 성공했는지 확인한다. 실패 호스트는 정책 교체를 되돌리기 전에 원인(예: 멀티파트 동작 거부)을 먼저 확인한다.
5. 같은 날 중앙 유지보수를 전체 대상으로 한 번 실행해 성공을 확인한다.

## 6. 호스트별 격리 확인 절차 (#374가 재사용)

호스트 키가 자기 버킷 밖에 접근하지 못하는지 정기적으로 확인한다.

1. 카나리(또는 임의 호스트) 호스트 키로 **다른 호스트 버킷**에 대해 목록 조회, 임시 객체 업로드, 읽기를 시도한다. 모두 거부여야 한다. 다른 호스트 버킷은 비공개 노트에서 고른다.
2. 같은 호스트 키로 버킷 목록 전체 조회(`ListAllMyBuckets`)가 거부되는지 확인한다.
3. 수집기 스냅샷에서 모든 `backup-prod-*` 서비스 계정의 정책 리소스가 자기 버킷 하나(버킷과 `버킷/*`)뿐이고, 정책 모양이 `host-key-policy.json`과 같은지 `diff`로 확인한다.
4. 거부 로그를 비공개 노트에 남기고 이슈에는 통과 여부만 적는다.

## 7. 롤백

- 트리거: 시험 1, 3, 4, 5 중 하나라도 실패, 또는 확대 후 첫 백업이 실패한 호스트가 있고 정책 교체가 원인으로 확인될 때.
- 절차: 해당 서비스 계정의 정책을 2절에서 기록한 기존 정책(기준선 스냅샷의 값)으로 되돌린다. 키는 바꾸지 않았으므로 호스트 쪽 변경은 없다. 되돌린 뒤 수동 백업으로 성공을 확인하고 수집기 스냅샷이 기준선과 같은지 `diff`한다.
- 롤백 중에는 호스트 키가 삭제 권한을 다시 갖는다는 점을 노트에 남기고, 원인 해소 후 다시 승인받아 재시도한다.

## 8. 중앙 유지보수 경로 확인 (계속 동작하는지)

1. 유지보수 키(`agents/rustfs`의 `maintenance_access_key`)는 이 변경으로 바뀌지 않는다. 정책을 건드리는 대상은 호스트 서비스 계정뿐이다.
2. 정책 교체 전후 모두 [backup.md](../backup.md) §7의 수동 실행으로 카나리 1대를 확인한다: `-e target_hosts=<카나리>`.
3. `backup_logs`의 `job=maintenance` 이벤트에서 `command=check`와 `command=forget`이 모두 `success=true`인지 본다. 8일 이상 `check` 이벤트가 없으면 "유지보수 누락" 알림이 발생한다.
4. 정책 변경 후 `forget --prune`이 실제로 데이터를 지울 수 있는지는 다음 보존 만료 때까지 알 수 없으므로, 확대 후 첫 주간 유지보수(일요일 05:00)의 성공 이벤트까지 확인한다.

## 9. Host Audit 연계

[#377](https://github.com/ppzxc/infra-automation/issues/377)이 백업 저장소 정책 점검을 Host Audit 항목으로 추가한다. 점검 기대치는 이 문서가 아니라 `roles/backup/files/host-key-policy.json`이다(삭제 허용은 `locks/*`뿐, 와일드카드 동작 없음).
