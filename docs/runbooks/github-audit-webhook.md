# GitHub 조직 감사 웹훅 런북

> GitHub 조직 웹훅으로 받는 관리 변경 이벤트의 수집 범위와 한계, 보완 절차, 출발지 대역 갱신, 서버 적용 절차를 적는다(Spec #399 / Ticket-7, #406). 수신기 설계는 [monitoring.md](../monitoring.md) §3-3, 전달 점검 작업은 [github_webhook_watch.md](../github_webhook_watch.md), 알림 대응은 [알림 런북](alerts.md)의 GitHub 절을 본다. **공개 저장소라 호스트 번호·주소·포트·수신 경로·조직명·시크릿 위치 세부는 적지 않는다.** 실제 값은 비공개 경로와 OpenBao 호스트 KV에만 둔다. 이 문서의 `<...>`는 자리표시다.
>
> **사용자 확정 사항(2026-11-03)**: 알림 등급(P1·P2·P3)과 구독 이벤트 13개는 사용자가 확정했다. 바꾸려면 알림 정의의 `severity`와 전달 점검 입력의 `expected_events`를 함께 바꾼다. 남은 확인은 Free 조직에서 웹훅 조회·재전송 API와 감사 로그 UI 내보내기가 되는지의 실측이다(PR 병합 전).

## 1. 수집 범위

조직 웹훅이 구독한 이벤트만 도착한다. 이벤트 이름은 전달 헤더(`X-GitHub-Event`)에만 있어 수집기가 헤더를 속성으로 보존한다. 출처는 GitHub 공식 문서(Ticket-1 조사)다.

### 1.1 수집되는 이벤트

| 이벤트 | 잡는 변경 | 주요 action |
|---|---|---|
| `repository` | 저장소 생성·삭제·이름 변경·공개/비공개 전환·보관·이전 | created, deleted, renamed, publicized, privatized, archived, transferred 등 |
| `public` | 비공개 저장소의 공개 전환 | action 없음 |
| `team` | 팀 생성·삭제·수정·저장소 연결 | created, deleted, edited, added_to_repository, removed_from_repository |
| `repository_ruleset` | 저장소 규칙 집합 변경 | created, deleted, edited |
| `personal_access_token_request` | 조직 PAT 접근 요청 처리 | created, approved, denied, cancelled |
| `meta` | 웹훅 자체 삭제 | deleted |
| `organization` | 조직 멤버 추가·초대·제거, 조직 이름 변경·삭제 | member_added, member_invited, member_removed, renamed, deleted |
| `member` | 저장소 collaborator 추가·권한 변경·제거 | added, edited, removed |
| `membership` | 팀 멤버십 추가·제거 | added, removed |
| `org_block` | 사용자 차단·해제 | blocked, unblocked |
| `branch_protection_rule` | 브랜치 보호 규칙 변경 | created, edited, deleted |
| `deploy_key` | 배포 키 추가·삭제 | created, deleted |
| `custom_property` | 조직 사용자 정의 속성 변경 | created, updated, deleted 등 |

- 행위자는 페이로드의 `sender`다. GitHub이 사용자를 확인하지 못하면 `ghost` 자리표시 계정이 오므로 이름으로 대조할 수 없다. 이때는 조직 감사 로그(웹 UI)로 실제 행위자를 확인한다.
- 이벤트별 대상 필드의 내부 구조와 `organization` action 목록의 완전성은 공식 문서로 확인하지 못했다(미확인). 실제 수신 샘플로 확인한 뒤 필드 추출([openobserve_config.md](../openobserve_config.md))을 보정한다.
- `repository.deleted`는 조직 웹훅만 받는다(저장소 웹훅·앱은 못 받는다). 페이로드가 25 MB를 넘으면 전달되지 않는다.
- 도착한 이벤트는 보안 로그 스트림의 `service_name=github-audit` 레코드로 남고, 위험한 변경 7종은 알림이 된다([알림 런북](alerts.md)).

### 1.2 수집되지 않는 이벤트 (공백)

웹훅은 "자원이 바뀌었다"는 이벤트만 보낸다. 아래는 웹훅 이벤트가 없거나 구독 대상이 아니라 **이 경로로는 보이지 않는다**.

| 공백 | 이유 | 보완 |
|---|---|---|
| 로그인(성공·실패) | 웹훅 이벤트가 없다 | 월간 웹 UI 감사 로그 내보내기 |
| 2FA 설정·해제 | 웹훅 이벤트가 없다 | 월간 웹 UI 감사 로그 내보내기 |
| 토큰 사용(PAT·SSH 키 사용, API 호출) | 사용 기록은 웹훅으로 오지 않는다(PAT 접근 *요청*만 `personal_access_token_request`로 온다) | 월간 웹 UI 감사 로그 내보내기, 토큰 만료일 관리 |
| Actions 설정 변경(허용 액션·러너·워크플로 권한 등) | 대응하는 웹훅 이벤트가 없다 | 월간 웹 UI 감사 로그 내보내기 |
| 시크릿 변경(Actions·Dependabot 시크릿 생성·수정·삭제) | 대응하는 웹훅 이벤트가 없다 | 월간 웹 UI 감사 로그 내보내기 |
| 웹훅이 꺼져 있거나 수신이 끊긴 동안의 이벤트 | GitHub은 실패한 전달을 자동 재전송하지 않고, 수동 재전송은 최근 3일 전달만 가능하다 | 전달 점검 작업이 6시간마다 재전송, 3일을 넘기면 월간 내보내기 |
| 웹훅 삭제 뒤의 모든 변경 | 훅이 없으면 전달이 없다 | 훅 삭제 알림과 전달 점검의 `missing` 판정, 내보내기 |
| 위 13개에 없는 기타 조직 설정·결제·보안 설정 변경 | 구독하지 않는다 | 월간 내보내기. 구독 추가 여부는 사용자가 확정한다 |

## 2. 수집 공백과 보완

보완은 조직 owner가 웹 UI에서 감사 로그를 내려받아 월간 로그 점검에서 훑는 것이다([월간 로그 점검 런북](monthly-log-review.md)의 GitHub 감사 로그 단계).

- 문서상 감사 로그 화면은 owner만 열 수 있고 최근 180일을 JSON 또는 CSV로 내보낼 수 있다(한도: 압축 100 MB 또는 처리 10분). API·스트리밍은 Enterprise Cloud 전용이라 쓰지 않는다.
- **Free 조직에서 화면과 내보내기가 되는지는 미확인이다.** 문서에 플랜 제한 언급이 없을 뿐 되는 근거도 없다. Ticket-1에서 확인하지 못했으므로 Ticket-8 서버 적용에서 실제 owner 계정으로 실측한다. 실측 결과(되는지, 어떤 이벤트가 보이는지)는 월간 점검 런북 해당 단계와 이 절에 갱신한다. 안 되면 1.2 공백 중 로그인·2FA·토큰·Actions·시크릿 변경은 이 저장소 범위에서 볼 방법이 없는 수용 위험으로 남기고 사용자에게 보고한다.
- 내려받은 파일은 조직 활동 기록이라 공개 저장소와 이슈에 올리지 않고 비공개 노트에 둔다.

## 3. 출발지 대역 갱신

입구(리버스 프록시)는 GitHub 웹훅 출발지 대역만 이 경로에 들인다. GitHub은 대역을 수시로 바꾸며(공식 안내: IP 허용 목록은 비권장, 쓰면 API를 지속 모니터링) 변경 통지 채널은 확인되지 않아(미확인) 정기 갱신이 필요하다.

- **주기**: 월간 로그 점검 때 확인하고, 전달 점검 알림 `infra-github-webhook-redelivery-failed`가 재전송 실패로 울리면 즉시 확인한다(대역 변경이 흔한 원인이다).
- **대역 출처**: GitHub 공개 API `GET /meta` 응답의 `hooks` 키(문자열 배열)다. 항목이 CIDR인지는 문서가 명시하지 않아(관례상 CIDR) 실측으로 확인하고, 미인증 호출 가능 여부도 실측한다.
- **구성 원칙**:
  1. 웹훅용 허용은 **별도 matcher**로 둔다. 기존 관리 경로의 허용 목록(whitelist)에 GitHub 대역을 섞지 않는다.
  2. 그 matcher와 핸들러는 **거부 핸들러(허용 목록 밖 거부)보다 앞**에 둔다. 단일 사이트 블록에서 거부가 먼저 평가되면 웹훅이 막힌다.
  3. 허용 조건은 **POST 메서드와 고정 경로 한정**이다. 출발지가 맞아도 다른 경로·메서드는 기존 거부로 떨어진다. 실제 경로 값은 저장소에 적지 않는다.
  4. 서명 검증(`X-Hub-Signature-256`)은 수신기가 하므로 출발지 제한은 추가 방어다.
- **입구 설정 파일 안전 변경**(기존 함정, [Uptime Kuma 이전 런북](kuma-migration.md)·[관리 웹 루프백 런북](mgmt-web-loopback-bind.md) 참조):
  - 입구 설정과 허용 목록은 **단일 파일 bind mount**다. `sed -i`는 새 inode를 만들어 컨테이너가 옛 내용을 계속 보므로 쓰지 않는다. 검증(`caddy validate`)은 통과하는데 반영이 안 돼 원인 찾기가 어렵다.
  - 줄 추가는 `>>`(inode 유지)로 호스트 파일에 붙이고 reload한다. 호스트 파일과 컨테이너가 같은 inode를 가리키는 정상 상태에서는 호스트 파일을 제자리에서 고치면 컨테이너도 같은 내용을 본다. 이미 `sed -i` 등으로 컨테이너가 옛 inode로 갈라진 경우에만(호스트 파일은 새 내용인데 컨테이너 안은 옛 내용) 컨테이너 안에서 `cat >`로 새 내용을 써서 컨테이너 쪽을 맞추고 reload한 뒤, 재생성 때 쓰이는 호스트 파일도 같은 내용인지 확인한다. 어느 쪽이든 반영 확인은 컨테이너 안에서 파일을 읽어 한다.
  - 컨테이너를 재생성하지 않고 reload만 한다. 환경변수로 읽는 값은 reload로 반영되지 않는다.
  - 자기 호스트에서 공인 도메인으로 시험하면 입구는 출발지를 컨테이너 네트워크 게이트웨이로 본다. 허용 시험은 그 출발지가 아니라 외부 출발지(GitHub의 테스트 전달)로 한다.
- **절차**(항목마다 승인):
  1. `GET /meta`의 `hooks`를 받아 비공개 경로에 저장하고, 직전 저장본과 diff한다. 변경이 없으면 종료한다.
  2. 입구 설정의 수정 전 사본과 해당 시점 스냅샷(4.1 기준선)을 비공개 경로에 보관한다.
  3. 승인을 받은 뒤 위 안전 변경 방식으로 대역을 갱신하고 reload한다. 추가·삭제된 항목만 diff로 확인한다.
  4. 조직 웹훅 화면에서 테스트 전달(ping)을 보내 2xx인지, 전달 점검 작업을 수동 실행해 `hook_status=ok`와 실패 전달 건수 0인지 본다.
  5. **롤백**: 수정 전 사본으로 덮어쓰기 복원(`sed -i` 금지)하고 reload한다. 판단 기준은 테스트 전달 실패, 입구 5xx 알림, 승인자의 중단 지시다.

## 4. 서버 적용 절차

저장소에는 입구·compose 원본이 없고(수동 관리 compose) 서버 적용은 사람이 한다. 이 절은 **서버 적용 티켓(Ticket-8)의 절차 원본**이다. 항목마다 운영자 승인을 받고 한 번에 한 항목만 적용한다. 값(호스트·주소·포트·경로·조직명·시크릿)은 비공개 경로와 OpenBao에만 두고 이슈·PR·커밋에는 통과 여부만 적는다.

**금지**: 시크릿 저장소 스택(overseer) 재생성, 방화벽 체인 변경, 시크릿 값 출력(`secrets.env`·env·KV 값을 열지 않고 권한·존재만 본다), 알림 등급·구독 이벤트의 임의 확정.

### 4.1 기준선과 스냅샷

1. 4.3 각 단계의 롤백 방법을 비공개 노트에 먼저 적는다.
2. 기준선 스냅샷을 수집하고 입구 설정·허용 목록·수집기 설정의 수정 전 사본을 보관한다. 같은 명령을 각 단계 뒤에 그대로 쓴다.

```bash
scripts/collect-security-baseline.sh --label <라벨> --ssh <계정>@<호스트>
```

3. 단계 뒤 스냅샷은 기준선과 **diff**해 승인한 변화만 있는지 본다. 방화벽 구간(`firewalld`, `nft-ruleset-stateless`, `iptables-docker-user`)은 항상 비어야 한다.

### 4.2 승인 전 확인

- 사용자 확정을 받은 알림 등급과 구독 이벤트 최종 목록(1.1의 13개 또는 조정안).
- 전달 점검용 토큰 발급(조직 Webhooks 권한, 만료일) 계획. 읽기와 재전송을 분리할 수 없다([github_webhook_watch.md](../github_webhook_watch.md)).
- 수신기를 켤 호스트가 modern 경로 호스트이고 수집기 버전이 수신기를 포함하는지.
- Free 조직에서 웹훅 REST API와 웹 UI 감사 로그 내보내기가 되는지 실측 계획(미확인, 2절).

### 4.4 단계 뒤 스냅샷 diff 판정

- S-1 뒤: 입구 설정 파일 diff가 의도한 matcher·핸들러 추가뿐이다.
- S-3 뒤: 수집기 설정 diff가 웹훅 수신기·파이프라인·`secrets.env` 항목 추가뿐이고 방화벽 구간 diff는 비어 있다.
- 모든 diff 원본은 비공개 경로에 두고 이슈에는 통과 여부만 적는다.

### 4.5 웹훅 시크릿 운반·폐기와 서명 시험

- **생성 위치**: 운영자 작업 단말에서 한 번 생성한다(임의 바이트를 인쇄 가능한 ASCII로, 파일은 `0600`의 임시 파일 하나). 저장소·이슈·비공개 노트 평문에는 두지 않는다.
- **운반**: 같은 값을 OpenBao 호스트 KV(S-2)와 GitHub 웹훅 시크릿 입력란(S-4)에 한 번씩만 넣는다. 셸 명령줄 인자나 환경변수로 값을 넘기지 않아 **셸 기록**(history)에 남기지 않는다(파일·표준입력으로 넘기고 명령줄에는 값을 쓰지 않는다). GitHub 화면에는 임시 파일을 편집기에서 열어 붙여 넣는다. **클립보드**에 값이 남지 않게 입력 직후 비우고 클립보드 기록 도구를 쓰지 않는다. 터미널 화면에 값을 출력(`cat`, `echo`)하지 않고 화면 공유·녹화·캡처 중에는 하지 않는다.
- **폐기**: S-2와 S-4 둘 다 끝나고 S-4의 폐기 전 서명 시험(정상·부정)과 ping 2xx가 **모두 통과한 뒤에** 임시 파일을 덮어써 지우고(`shred` 또는 같은 효과의 도구) 클립보드·셸 기록에 값이 없는지 확인한다. 노출이 의심되면 새 값을 만들어 S-2와 S-4를 다시 한다. GitHub 쪽 값은 나중에 읽을 수 없으므로 일치 여부는 비교하지 않고 **ping 2xx로만 검증**한다.
- **올바른 서명 시험**: 부정 시험(틀린 서명·헤더 없음·본문 변조 401)만으로는 수신이 되는지 모른다. 올바른 서명도 시험한다. 시험용 본문에 대해 시크릿으로 HMAC-SHA256을 계산해 `X-Hub-Signature-256: sha256=<16진수>` 헤더를 붙여 보내면 2xx여야 한다. 계산은 시크릿을 명령줄에 쓰지 않는 방식(파일에서 읽기)으로 한다. 실제 시크릿 대신 GitHub 공식 테스트 벡터는 수신기 시험(`tests/test_github_webhook.py`)에서 이미 확인한다.
- **시험 출발지**: 호스트 자신에서 공인 도메인으로 시험하면 입구가 출발지를 컨테이너 네트워크 게이트웨이로 보아 허용 대역 밖이라 막힌다. 그래서 수신 호스트에서 **브리지 주소로 직접** 보내 수신기 서명·경로 동작을 시험하고(입구를 거치지 않는다), 입구의 출발지·경로·메서드 제한은 외부 출발지(GitHub 테스트 전달)로 따로 확인한다.

## 5. 롤백

적용 전에 쓴다. 롤백도 overseer 스택은 건드리지 않는다.

| ID | 되돌림 |
|---|---|
| R-1 | 보관한 입구 설정 수정 전 사본으로 덮어쓰기 복원하고 reload한다(`sed -i` 금지). 기존 경로 응답이 기준선과 같은지 본다 |
| R-2 | KV 5개 키를 제거하거나 `otel_github_webhook`을 끈다(전체를 읽어 합쳐 `cas`로 쓴다). 시크릿은 노출 의심 시 교체한다 |
| R-3 | S-3 단계의 롤백이다. `otel_github_webhook`을 끄고 Host Agents를 같은 호스트에 다시 배포한다. 끈 호스트는 수신기·파이프라인·`secrets.env` 항목·링크가 없어져 렌더링 결과가 이전과 같다(`MON-072`가 `docker.service.wants` 링크도 정리). 바인딩 실패로 수집기 전체가 멈춘 경우 기준선의 수집기 설정 사본으로 복원하고 수집기를 재시작한다 |
| R-3b | 도커가 멈춘 채면 즉시 `systemctl start docker`로 올린다(재생성하지 않는다). 시작 뒤 수집기(`otelcol-contrib`)·입구 프록시·기존 컨테이너가 모두 active인지, 같은 호스트의 overseer 스택 서비스가 응답하는지 확인한다. 수집기가 올라오지 않으면 R-3으로 수신기를 끈다. 컨테이너 안 서비스가 올라오지 않으면 compose `up`으로 다시 만들지 말고 개별 `start`로 되살리고 승인자에게 보고한다 |
| R-4 | 조직 웹훅을 비활성화하거나 삭제한다. 삭제는 `meta` 알림과 전달 점검 `missing`이 뜨므로 점검 작업을 먼저 멈춘다(R-5) |
| R-5 | Semaphore 템플릿 예약을 끈다. 입력 KV는 R-2 |
| R-6 | 시험 변경을 되돌리고 알림 정의를 이전 버전으로 반영한다. 이때도 먼저 `o2c_plan_only`로 계획을 보고 삭제 대상이 폐기 목록에 한정되는지 서버 알림과 비교한다. 새 알림을 되돌리면 이름이 정의에서 빠지므로 **옛 이름을 `o2c_retired_alerts`(폐기 목록)에 더해야 서버에서 지워진다**. 목록에 없으면 서버에 남고, 목록에 다른 이름이 섞이면 의도하지 않은 알림이 지워지므로 이름을 하나씩 대조한다 |

롤백 뒤에도 같은 스냅샷 명령으로 diff가 비는지 확인한다. 중단 판단 기준은 기존 관리 경로 장애, 수집기 중단(`system_logs` 수집 끊김), 승인자의 중단 지시다.

## 6. 서버 적용 뒤 검증

[monitoring.md](../monitoring.md) §3-3에 미확인으로 적힌 항목을 서버에서 실측한다.

1. `MON-071`~`MON-073`: 켠 호스트에 `docker.service.wants/otelcol-contrib.service` 링크가 있고 끈 호스트(기능을 끈 기존 호스트 포함)에는 없다.
2. (S-3b에서만, 별도 승인·유지보수 창) `systemctl stop docker` → `start docker` 뒤 수집기가 active이고 수집이 이어진다. 도커 정지 동안 그 호스트의 전 컨테이너와 수집기가 멈춘다.
3. (S-3b에서만) `systemctl restart docker`로 브리지가 재생성된 뒤 수신 소켓이 새 브리지 주소에 다시 열렸다(재바인딩). 도커보다 먼저 올라와 실패해도 `Restart=always`가 재시도한다.
4. `MON-069`/`MON-070`: 게이트웨이와 바인딩 주소가 다르면 변경 전에 실패한다. 네트워크 재생성·서브넷 변경 뒤에는 KV 주소와 입구 대상 주소를 새 게이트웨이로 맞추고 Host Agents를 다시 배포한다.
5. 서명 시험(올바른 서명 2xx, 부정 401)은 S-4의 '폐기 전 서명 시험'에서 이미 수행했다(4.5). 여기서는 그 결과를 확인만 하고, 임시 파일이 폐기된 뒤에는 서명 시험을 다시 하지 않는다. 허용 밖 출발지·다른 경로·GET이 입구에서 거부되는지는 외부 출발지로 확인한다.
6. 헤더 속성(`header.X-Github-Event` 등)이 OpenObserve에서 문자열로 보이고 `github_event`·`github_action` 필드가 채워진다.
7. Free 조직에서 웹훅 REST API(목록·전달 목록·재전송)가 동작하는지와 웹 UI 감사 로그 내보내기 가능 여부(미확인 해소). 결과를 2절과 월간 점검 런북에 반영한다.
8. 전달 목록의 보존 기간(재전송 가능 3일만 확정, 목록 보존은 미확인)을 실측하고 점검 주기(6시간)가 충분히 짧은지 확인한다.
